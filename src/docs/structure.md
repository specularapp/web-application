# Estrutura e stack

## Stack

| Tecnologia | Papel |
| --- | --- |
| Next.js 16 (App Router) + TypeScript | Front e camada de servidor (Server Components, Server Actions, Route Handlers) |
| Supabase | Autenticação, banco Postgres com RLS, storage |
| Redis (ioredis) | Cache de leituras repetidas e rate limit |
| Resend | E-mail transacional e de automação |
| Stripe | Pagamentos e recebimentos (o doc original dizia "strapi", que é um CMS; a integração é Stripe) |
| n8n | Automações e integrações externas via webhooks |
| Emotion (`@emotion/styled`) | Styled components, consumindo os tokens CSS |
| cmdk | Paleta de comandos |
| Phosphor Icons | Ícones |
| zod | Validação de entrada no servidor |
| ESLint + jsx-a11y | Qualidade e acessibilidade |

## Organização de pastas

```
src/
  app/                  rotas (apenas roteamento, sem lógica de domínio)
    previa/             prévias de front, só em homologação (fora dela a página é 404 e o proxy fecha)
    (marketing)/        site público: home, preços, termos, privacidade
    (auth)/             login, cadastro, recuperação de senha
    (app)/              área autenticada, protegida pelo proxy
    api/v1/             mesma regra das actions exposta ao aplicativo, por Bearer token
    (public)/           páginas compartilháveis com clientes: portfólio, currículo, orçamento, contrato, cobrança
    api/                health e webhooks (stripe, n8n, resend)
    auth/callback/      troca de código do Supabase
    componentes/        vitrine do design system, pública e noindex
  components/
    ui/                 primitivos reutilizáveis (Button, Input, Card)
    layout/             shell da aplicação (Sidebar, Topbar)
    providers/          providers globais (Emotion, tema)
  features/<dominio>/   regra de negócio por domínio: actions, queries, schemas e componentes específicos
  hooks/                hooks compartilhados
  lib/                  clientes das integrações, metadata, env, segurança, utilitários
  styles/               reset.css, tokens.css, globals.css
  types/                tipos globais e tipos gerados do banco
  docs/                 regras, objetivo e estrutura
  proxy.ts              headers, sessão, MFA e proteção de rotas
db/
  README.md             convenções de banco e migrações
  migrations/<dominio>/ fonte da verdade das migrações, por domínio
  supabase/             projeto do Supabase CLI (config, seed; migrations é gerada)
```

## Domínios em `features`

`auth`, `organizations`, `onboarding`, `dashboard`, `crm`, `clients`, `catalog`, `quotes`, `contracts`, `billing`, `projects`, `tasks`, `portfolio`, `resume`, `finance`, `automations`, `ai`, `gamification`, `settings`.

## Convenções

- Rotas em português, código em inglês.
- Páginas só compõem componentes de `features` e `components`.
- Estilo sempre com tokens de `styles/tokens.css`. Primitivos sem interação (Text, Stack, Container, Table, Label, Field, Logo...) são Server Components com CSS Modules (`*.module.css` ao lado do componente, variantes por `data-*`), zero JS no cliente. Componentes interativos (Button com loading, Dialog, Switch, Toast...) usam Emotion e `"use client"`. Nada de valores soltos.
- Todo componente novo entra na vitrine `/componentes` com nome e exemplo, conferido nos dois temas.
- Tela grande também ganha prévia em `/previa/*`, que é a vitrine no formato de verdade: tela cheia em vez de caixa, para ajuste visual sem sessão e sem dado no banco. `/previa/primeiros-passos` abre qualquer uma das três etapas por `?etapa=time|membros|plano`, e na etapa do plano escolher um plano pago abre a etapa de pagamento com o espaço do formulário do Stripe reservado. `/previa/plano` mostra `/configuracoes/plano` com assinatura em teste, cartão e faturas de exemplo. `/previa/painel` mostra o painel inteiro, menu e blocos, com os dados de exemplo do menu. As rotas existem só em homologação: o proxy libera o prefixo `/previa/` por `isHomologation()` e a própria página devolve 404 fora dela. Os estados de exemplo vivem num lugar só, em `features/billing/preview.ts`, compartilhados com a vitrine.
- `OnboardingFlow` separa `demo` (não toca o servidor) de `boxed` (caixa dentro da página, o formato da vitrine): a prévia usa só `demo`, então ela aparece como a camada de verdade.
- Identificador que a pessoa vê é sempre o mesmo formato, em toda a aplicação (decisão de 2026-09-07): prefixo de três letras do domínio, ano e sequência de quatro dígitos, como `ORC-2026-0042`, por `formatReference` em `lib/utils/reference.ts` (`ORC` orçamento, `CTR` contrato, `COB` cobrança, `PRJ` projeto). A sequência reinicia a cada ano e cresce além de quatro dígitos se precisar; o id interno continua sendo o do banco. Nasceu no bloco de último orçamento, quando o usuário pediu um número curto e objetivo em vez de um código longo.
- Metadados via `createMetadata` em toda página.
- Dados via Server Components e Server Actions. Cache em Redis onde houver leitura repetida.
- Webhooks verificam assinatura. Toda entrada validada com zod no servidor.

## Fluxo de dados

1. Página (Server Component) chama `queries` da feature.
2. `queries` acessam Supabase pelo cliente de servidor, com cache em Redis quando fizer sentido.
3. Mutações passam por `actions` (Server Actions) com validação zod e revalidação por tag.
4. Eventos externos entram por `app/api/webhooks/*`, são verificados e despachados para a feature ou para o n8n.

## Design

### Cores

Paleta de cores do sistema Apple (Human Interface Guidelines, System colors), em `src/styles/tokens.css`:

- Primitivos `--sys-*`: red, orange, yellow, green, mint, teal, cyan, blue, indigo, purple, pink, brown e gray 1 a 6.
- Fundo do tema claro é `#fbfbfc`, e não branco puro (decisão de 2026-09-02): branco seco endurece a tela e some com a borda dos cartões, que são brancos de verdade (`--color-bg-tertiary`). O escuro segue em preto puro.
- Semânticos `--color-*` seguindo os nomes da Apple: label (4 níveis), placeholder, link, separator, bg (system e grouped, 3 níveis cada) e fill (4 níveis).
- Papéis do produto: `--color-brand` (preto no claro, branco no escuro, igual ao logo), `--color-accent` (system blue), success, warning, danger, info e focus.
- Claro e escuro com `light-dark()`, forçados com `data-theme="light"` ou `data-theme="dark"` no `html`. **Escuro é o padrão do produto**: sem cookie de preferência, o layout raiz põe `data-theme="dark"` em vez de seguir o sistema (decisão de 2026-09-01). Todo componente continua obrigado a funcionar nos dois temas, porque o claro segue disponível por preferência.

### Tipografia

- Inter (`--font-sans`) como principal, Geist Mono (`--font-mono`) só para código, Playfair Display (`--font-serif`) para títulos editoriais. Todas via `next/font`.
- Número é sempre Inter: `numeric` no `Text` liga `tabular-nums` e força `--font-body`, mesmo sobre `font="code"`. Nada de trocar de família para alinhar algarismo.
- Use `--font-body`, `--font-code` e `--font-display`, que já incluem os fallbacks.
- Escala de tipos da Apple: caption 2 e 1, footnote, subheadline, callout, body, headline, title 3 a 1 e large title.
- Tracking sai do tamanho, não do gosto: `--tracking-tightest` (-0.06em) de 22px para cima, `--tracking-tighter` (-0.04em) entre 16px e 20px, `--tracking-tight` (-0.02em) até 15px. Texto grande precisa de mais aperto que texto pequeno.

- Uma família só desde 2026-09-04: `--font-code` e `--font-display` apontam para a Inter, e Geist Mono e Playfair deixaram de ser carregadas. Os tokens ficam porque dizem o papel do texto; trocar a fonte de um papel volta a ser um lugar só.

### Controles

- Altura e respiro em `--control-height-*` e `--control-padding-*`, nos tamanhos `sm`, `md` e `lg`.
- `--touch-target` garante 44px em ponteiro grosso. O helper `controlMetrics` de `src/components/ui/styles.ts` aplica os três de uma vez.
- Cor de botão e de controle sai de variáveis locais (`--button-background`, `--button-foreground`, `--button-border`), definidas por `data-variant` e sobrescritas por prop quando precisar de cor sob medida.
- Botão cobre a família inteira por prop: texto puro, `iconStart`, `iconEnd`, `iconOnly` (quadrado, exposto como `IconButton` com `label` obrigatório) e `locked` com `plan`, que anexa a etiqueta do plano sem tirar o clique, para o clique levar ao upgrade.
- **Botão com `href` é o `Link` do Next**, e não `<a>` cru (2026-09-08): navegação de cliente com prefetch, e o corpo do botão lê o `useLinkStatus` do próprio link para trocar o glifo pelo giro enquanto a página de destino não chega. Até então cada botão com endereço era recarga inteira e o clique parecia não pegar; foi o relato do "Editar" sem resposta que revelou.
- `loading` é o estado de espera de toda ação: o `Spinner` toma o lugar do `iconStart`, o botão se desabilita sozinho e ganha `aria-busy`, com opacidade 0.75 e cursor `progress` para não se confundir com o desabilitado (0.4). O spinner puxa `currentColor` e `--diameter: 1.2em` pela regra do próprio botão, então acompanha variante e tamanho; o rótulo do `Spinner` fica vazio de propósito, porque quem anuncia é o texto do botão, que troca para o gerúndio ("Entrando", "Salvando"). Nos formulários com `useActionState` vem de `pending`; nos botões de provedor OAuth, que são um `<form>` por botão sem estado próprio, vem do `useFormStatus` dentro de um subcomponente.

### Campos de formulário

- Fonte com piso de 16px por `fieldMetrics`. Abaixo disso o iOS dá zoom ao focar, e a escala de tipos tem tamanhos de 13 e 15px, então o piso não é opcional.
- Rótulo, caixa do campo e dica compartilham a mesma borda esquerda, sem recuo óptico. O rótulo recuado até o texto digitado foi testado e descartado: parece deslocado.
- No toque não há anel de foco nenhum (`reset.css`, `@media (hover: none)`, 2026-09-08, a pedido): sem teclado ele não guia ninguém, e em alguns navegadores de celular acendia azul depois do dedo em botões e linhas de menu. Vai com peso para passar por cima da folha do calendário, que declara o próprio anel.
- Campo de texto não tem indicador de foco, por decisão de produto. É desvio consciente de `rules.md`, que exige foco visível: quem navega por teclado perde a referência de onde está. Botão e link mantêm o anel.
- Máscara sai da prop `mask` do `Input`, com os padrões em `src/lib/masks.ts`: `cpf`, `cnpj`, `document` (troca de CPF para CNPJ ao passar de 11 dígitos), `phone` (fixo ou celular pelo comprimento), `cep`, `date`, `currency`, `percent` e `integer`. Nunca escrever regex de máscara solta em feature.
- Máscara numérica preenche a partir do centavo: o valor bruto é a sequência de dígitos e a formatação divide por 100 com `Intl.NumberFormat` em pt-BR. Digitar 1, 2, 3 dá R$ 0,01, R$ 0,12, R$ 1,23. É por isso que dinheiro vai para o banco em centavos inteiros: o campo já entrega assim.
- Máscara de tamanho variável (telefone, documento) usa `NumberFormatBase` com `format` por função, nunca `PatternFormat` com padrão trocado por estado. `PatternFormat` corta o dígito que passa do número de marcadores do padrão atual, então com o padrão de 10 dígitos o 11º nunca chega e celular fica impossível de digitar.
- O anel de foco some, mas o estado de erro fica: borda vermelha no `FieldShell`.
- Unidade fica fora do valor: `R$` e `%` são um `FieldAffix` em semibold ao lado do controle, e o campo guarda só o número. Texto dentro de `input` não aceita peso parcial, então o afixo tem que ser elemento próprio.
- Data é seleção, não digitação: `DatePicker` sobre o `react-day-picker`, com mês e ano em lista. O popover vai por portal para o `body`, porque dentro do campo ele ficaria atrás do campo seguinte, pintado depois na ordem do DOM. Posição por `fixed`, abaixo quando cabe e acima quando não cabe. A máscara `date` continua para quem precisa digitar.
- `Textarea` (2026-09-08) é o `Input` esticado em linhas: o `textarea` cru dentro do mesmo `FieldShell`, com o mesmo piso de fonte, o mesmo estado de erro e a alça só na vertical, porque a largura é do formulário. Nasceu com a ficha do cliente.
- `FieldShell` é o invólucro comum de todo campo: borda, raio por tamanho, estado inválido e desabilitado. Fundo transparente, o mesmo do botão `outline`, para campo e botão lerem como a mesma família sobre qualquer superfície; no escuro o fundo elevado destoava do botão ao lado. `Input` e `DatePicker` só põem o controle dentro. O canto é `corner-shape: squircle` nativo, declarado direto, e fica fora do recorte do fallback por conter o controle e os afixos.
- No mobile (abaixo de 48rem) o calendário vira **bottom sheet**: fixo na base, largura total, alça no topo, fundo em `--color-scrim`, página travada atrás, células maiores. O popover flutuante depende de medir o gatilho e reagir a rolagem e teclado virtual, o que no celular vira salto e recorte. `useMediaQuery` em `src/hooks` decide, com `useSyncExternalStore` para não divergir na hidratação.
- A legenda do calendário (mês e ano) é nossa, via `components.MonthCaption` do `react-day-picker` com `useDayPicker().goToMonth`. O `captionLayout="dropdown"` da lib usa `<select>` nativo, e a lista de um select é desenhada pelo sistema: não aceita fonte, raio, sombra nem cor. O `CaptionDropdown` é um listbox de verdade (`role="listbox"`, `aria-activedescendant`, setas, Home, End, Enter, Escape), com a opção atual marcada e rolada para a vista ao abrir.
- Esse listbox é o `Listbox` de `components/ui/listbox/`, genérico em `string | number`, com `placement` (`below` ou `above`, que vira dropup e troca o caret) e `prefix` (rótulo curto antes do valor, como "Mostrar 30"). Saiu do calendário no segundo uso, a `Pagination`.
- `actions` põe itens que executam em vez de escolher (remover, cancelar) no fim da lista, separados por um divisor, com `tone="danger"` quando destroem algo. Ação e opção dividem a mesma navegação, e é por isso que o item ativo passou a ser índice e não valor: seta e Enter precisam alcançar um item que não é um valor possível do campo. Substitui o botão solto ao lado do campo, que roubava espaço da linha e precisava de um lugar reservado para não desalinhar.
- `placement="auto"` decide o lado ao abrir, comparando o espaço abaixo do gatilho com a altura estimada da lista (número de opções pela altura fixa da opção, com teto). É estimativa e não medição porque medir só depois de montar faria a lista aparecer embaixo e pular para cima no mesmo quadro.
- `Select` é esse mesmo `Listbox` vestido de campo, não outro componente: o gatilho recebe altura, recuo, raio e fonte do tamanho de controle pelas variáveis locais (`--listbox-trigger-height`, `--listbox-trigger-padding`, `--listbox-trigger-radius`, `--listbox-trigger-font-size`, `--listbox-trigger-border`), com piso de 16px na fonte pelo mesmo motivo do `Input`. O valor sai num `input type="hidden"`, então funciona dentro de `form` sem JS de cola; `placeholder` aparece enquanto ninguém escolheu e o `id` vai para o gatilho, para o `Label` do `Field` apontar para ele. Não usa `select` nativo porque a lista do nativo é desenhada pelo sistema e não aceita fonte, raio nem cor.
- Largura de componente Emotion nunca sai de classe de CSS Module: a folha do Emotion é injetada em runtime, depois da do módulo, e com a mesma especificidade ela vence. Quem precisa apertar um `Select` numa linha (a lista de membros) põe o componente dentro de um `span` próprio e dimensiona o `span`.
- O gatilho do `Listbox` é estilizado por variáveis locais (`--listbox-trigger-height`, `--listbox-trigger-radius`, `--listbox-trigger-background`, `--listbox-trigger-background-hover`), com o visual do calendário como padrão. Quem o embute define as variáveis, sem `className` de fora.
- Ids de opção saem do índice, não do valor: `aria-activedescendant` é um IDREF e valor com espaço quebraria.
- As opções ficam em grid com 2px de respiro (`--space-half`), para o fundo da ativa e da selecionada não colarem uma na outra.
- Barra de rolagem interna é sempre `thinScrollbar` de `src/components/ui/styles.ts`: 6px, trilho transparente, polegar em `--color-fill-quaternary` que escurece no hover. Vale para listbox, tabela e qualquer painel que rola dentro de si; a rolagem da página fica com a barra do sistema.
- Rolar item para a vista dentro de um painel é `scrollTop` no próprio painel, nunca `scrollIntoView`: esse rola todos os ancestrais, e num popover fixo isso arrasta a página inteira.
- O calendário é todo neutro: hoje leva anel fino em `--color-separator`, selecionado leva `--color-brand`, foco leva `--color-label`. O acento azul fica de fora dessa parte por decisão de produto.
- A bolha de erro fica **sempre acima** do campo: para baixo ela cairia atrás do campo seguinte, que é pintado depois na ordem do DOM. Para cima, ela cobre o campo anterior, que já foi pintado.
- `Tooltip`: Geist Mono em footnote (13px) com peso medium, respiro de 8 por 12, raio `--radius-md` e canto nativo. Um só `--bubble-radius` alimenta o raio da bolha, o recuo da seta e o alinhamento, então mudar o raio não desalinha nada.
- A seta do `Tooltip` cai no centro do gatilho por geometria, não por medição: a bolha alinhada ao fim tem a borda a `raio + metade da seta` do centro do gatilho, e a seta fica a `raio` da borda da bolha. Os dois números se cancelam e o centro coincide em qualquer largura de gatilho.
- Preenchimento automático não pinta o campo: o `reset.css` cobre o fundo do navegador com `box-shadow` inset em `--field-background`, que cada campo declara com a própria superfície.
- O controle vive dentro de um `<span>` que carrega borda, raio e squircle, porque `input` é elemento substituído: não aceita filho, nem afixo, nem ícone dentro.
- `Checkbox` segue a mesma ideia: o `input type="checkbox"` nativo fica invisível por cima (opacidade zero, cobrindo o rótulo inteiro), e o quadrado desenhado é um `<span>` de 20px em `display: grid` com o ícone centrado por `place-items`, borda CSS de 1,5px e `corner-shape: squircle` nativo no raio `sm`. O raio `xs` foi testado e parecia quadrado: a superelipse é mais reta que o arco de círculo no mesmo raio, e em 20px isso some. Estado sai de `:has(input:checked)`, `:has(input:indeterminate)`, `:has(input:focus-visible)` e `:has(input:disabled)` no invólucro, que troca variáveis locais; nenhum JS além de escrever `indeterminate`, que só existe como propriedade do DOM. Marcado e indeterminado pintam `--color-brand` com o traço em `--color-bg`, o mesmo par do botão primário. Com `children` o invólucro é `label`; sem, é `span` e quem usa passa `aria-label` ou associa um `Label`.
- `Switch` é o mesmo esqueleto com `input type="checkbox" role="switch"`. Trilho em pílula (`--radius-full`, que por regra não declara canto) de 28 por 64 com 2px de folga, polegar largo de 36 por 24 que desliza por `translate` calculado a partir das próprias variáveis (`largura - polegar - 2 folgas`), então mudar um tamanho não desalinha o outro. `sm` é 20 por 44 com polegar de 24. Ligado é `--color-success`, o verde do sistema, como no iOS; desligado é `--color-fill`. Polegar em `--color-on-accent` (branco nos dois temas, como o iOS) com `--shadow-sm`. `prefers-reduced-motion` desliga a transição do deslize.

### Etiquetas

- **O teto de cada campo de texto sai do schema, num número só** (2026-09-10, a pedido): cada domínio exporta os limites (`quoteLimits`, `clientLimits`, `catalogLimits`, `organizationLimits`) e daí saem tanto o `.max()` do zod quanto o `maxLength` do campo na tela, então o campo para de aceitar no mesmo ponto em que o servidor recusaria. Sem o teto no campo, o zod barrava no envio mas a tela já tinha desenhado: um título de mil caracteres estourava o cabeçalho da folha do documento e o cartão da lista, e a pessoa só descobria ao salvar. Dois números para a mesma regra é como eles saem de sincronia, então nenhum `maxLength` traz valor escrito à mão. O `TagInput` ganhou `maxLength` para o texto de cada etiqueta, ao lado do `max` que já limitava a quantidade.
- `Badge` é a etiqueta de situação, categoria e contagem. Server Component com CSS Module, sem JS.
- **O tamanho pequeno respira, e por igual nos quatro lados** (dois acertos de 2026-09-10, do relato de que as etiquetas de situação estavam feias): ele vivia em 20px de altura com texto de 11px e o glifo saindo em 13px, e a etiqueta lia como um selo colado. Passou a 22px com o texto de 12px, o mesmo do tamanho padrão. Na primeira rodada o recuo lateral foi para 10px, o que deixou a folga de cima e de baixo em metade da dos lados e a etiqueta lendo esticada na horizontal; agora o lateral é 6px, uma proporção de 1,6 no lugar de 2,0. A altura não subiu para 24 de propósito: ali o pequeno ficaria do tamanho do padrão e a escala perderia o degrau. Os 22px cabem na linha de 36px da densidade compacta.
- **Um matiz gera tudo.** Cada `tone` define só `--badge-hue`; o CSS deriva três cores dele e nenhuma variante escolhe cor própria:
  - `--badge-ink`: matiz misturado com `--color-label` em 70/30. No claro puxa para o preto, no escuro para o branco, então o mesmo cálculo dá contraste AA nos dois temas. Amarelo é o único que precisa de 60/40.
  - `--badge-tint`: matiz em 14% de alfa no claro e 18% no escuro, por `light-dark()` sobre `color-mix()`. Alfa, e não cor opaca, para a etiqueta assentar em qualquer superfície.
  - `--badge-line`: matiz em 36% e 44%, para a borda do contorno.
- Variantes só recombinam as três: `soft` (tinta sobre tint), `solid` (tinta como fundo e `--color-bg` como texto, o mesmo par de `--color-danger-solid` e `--color-on-danger`) e `outline` (tinta sobre transparente com a linha).
- Tons em dois grupos: papéis do produto (`neutral`, `brand`, `accent`, `success`, `warning`, `danger`, `info`) para situação com significado, e a paleta inteira (`red` a `brown`) para categoria em que a cor é arbitrária. `hue` por prop aceita uma cor escolhida pelo usuário, como etiqueta de CRM, sem sair do modelo.
- Tamanhos e raios saem juntos: `sm` 20 de altura e raio 8, `md` 24 e raio 8, `lg` 28 e raio 12. Canto por `squircle()` com `clip` nas variantes sem borda, para o fallback recortar o fundo; `shape="pill"` fica no `round` e não declara nada.
- Só ícone exige `label`, que vira texto para leitor de tela, no mesmo contrato do `IconButton`. O tipo obriga: ou `children`, ou `icon` com `label`.
- Ícone herda `currentColor` e o peso `bold` que casa com o texto semibold, pelo `matchIconWeight` de `components/ui/icons.ts`, compartilhado com o Button. Não existe variante com ponto colorido (dot), por decisão de produto: a cor do texto e do fundo já dizem a situação.
- Etiqueta com remoção (o × do chip) é outro componente, interativo, e não entra aqui.

### Avatar

- `Avatar` recebe `name` e, opcionalmente, `src` e `seed`. Sem imagem entra o rosto do DiceBear no estilo Adventurer (`@dicebear/core` e `@dicebear/adventurer`, por `avatar/shape.ts`, o único ponto que importa a lib), desenhado a partir do `seed`, com o e-mail como semente para o avatar não mudar quando o nome muda.
- **O rosto gerado vem de uma rota, e não embutido na página** (varredura de peso de 2026-09-08). O `Avatar` monta `<img src="/api/avatar/{token}.svg">` e a rota (`app/api/avatar/[token]/route.ts`) desenha e devolve com `cache-control` de um ano e `immutable`. Antes o SVG do Adventurer, uns 11 KB, ia inteiro na marcação e de novo, escapado, na carga do RSC: no painel eram 42 rostos à vista e mais uns 70 dentro de janelas fechadas, somando **1 MB dos 1,67 MB da página**. Pela rota a mesma pessoa em cinco lugares custa uma requisição, e na segunda visita custa zero. `<img>` cru, e não `next/image`: o otimizador não mexe em SVG sem `dangerouslyAllowSVG`, que rebaixaria a segurança sem ganhar nada; é desvio consciente da regra de imagens.
- **O endereço leva um token, e não a semente.** `avatarToken` deriva o token por duas passagens de hash (cerca de 64 bits) e é ele que vira a semente do desenho. A semente costuma ser o e-mail da pessoa, e e-mail em endereço de imagem vaza para registro de acesso, cache de borda, `Referer` e histórico do navegador, o que num produto que guarda dado de cliente não se faz. O token é determinístico e sozinho basta para redesenhar, então a rota não guarda mapa nenhum. Consequência aceita: como a semente do desenho mudou, os rostos gerados ficaram diferentes dos de antes, uma vez só; nenhum avatar é persistido, e daqui para frente cada pessoa tem sempre o mesmo. O matiz do fundo continua saindo da semente original, então a cor de cada pessoa não mudou.
- A rota é pública por construção (o `matcher` do proxy já pula `/api`) e não expõe dado: token não volta a ser e-mail. Ela devolve `default-src 'none'` e `nosniff` no próprio arquivo, porque SVG na mesma origem é vetor de script quando o conteúdo escorrega, e aqui o conteúdo é gerado pela lib a partir de um token que casa com `[a-z0-9]`. **Fica sem rate limit, ao contrário do que `rules.md` pede para rota pública**: cada resposta é `immutable` e some no cache da borda, o trabalho por requisição é de um milissegundo com cache em memória por token, e um limite por Redis somaria ida e volta a cada um dos rostos da primeira carga, que é justamente o que a mudança veio cortar. Se algum dia a rota aparecer em pico de origem, o limite entra aqui. Trocou o `avvvatars-react` em 2026-09-04, a pedido: rosto no lugar de forma abstrata; o estilo foi Lorelei até 2026-09-05, quando virou Adventurer, também a pedido. Iniciais continuam descartadas, por decisão de produto. O SVG é gerado em código, sem DOM, então sai igual no servidor e no cliente, sem folha injetada nem nonce (o `GooberNonce` saiu junto). O único `id` do SVG é reescrito com o hash da semente, porque a mesma máscara em vários avatares colidiria e o `randomizeIds` da lib usa Math.random, que discordaria na hidratação; o `<metadata>` sai para não pesar em cada avatar.
- O fundo do rosto é um matiz da paleta do sistema escolhido pela mesma semente (`hashString` de `lib/utils/hash.ts`, o mesmo da frase do dia), em pastel a 32% sobre o branco fixo (`--color-on-accent`), igual nos dois temas: o traço do Adventurer é escuro e sumiria sobre fundo escuro, e o pastel opaco é o que deixa um avatar cobrir o vizinho no grupo. O raio e o recorte continuam no invólucro, que já esconde o overflow por causa da foto, então círculo e squircle saem de um lugar só.
- Foto de perfil do Google e do GitHub entra sozinha: o gatilho `handle_new_user` copia do metadata no cadastro e `handle_user_identity` faz o mesmo quando a identidade é vinculada depois, sempre com `coalesce`, para nunca sobrescrever o que a pessoa definir no produto. Com imagem usa `next/image` com `fill` e `sizes` fixo por tamanho; domínio remoto entra em `remotePatterns` quando o upload existir. Server Component com CSS Module.
- Tamanhos na escala dos controles: `xs` 24, `sm` 36 (`--control-height-sm`), `md` 44, `lg` 52. Círculo por padrão. `shape="squircle"` usa raio em metade do lado, que é a escala do botão de ícone (`--icon-button-radius-*`; `xs` usa `--radius-md`), então avatar e `IconButton` do mesmo tamanho têm o mesmo contorno.
- Canto por `squircleAuto()` quando `shape="squircle"`: nativo onde há `corner-shape`, e no fallback o recorte por `clip-path` entra sozinho porque o avatar já tem `overflow: hidden` para a imagem. O anel do grupo é `box-shadow` no próprio elemento e não é recortado.
- `AvatarGroup` só sobrepõe: cada avatar seguinte entra 8px sobre o anterior, e todos ganham anel de 2px em `--color-bg` por `box-shadow`, que não ocupa layout e não é recortado pelo `overflow` do próprio avatar. Sem contador "+N" por enquanto.

### Toast

- Todo toast tem ícone, título, descrição e um botão de ação, sem botão de fechar. Sem `action` o botão vira "Entendi" e só fecha. Contrato e comportamento em `libs.md`.
- `Toast` em `components/ui/toast/` é só o visual, e por isso aparece estático na vitrine. Fila, timer e posição ficam no `ToastProvider` de `components/providers/toast-provider/`, montado no layout raiz dentro do `EmotionRegistry`. `useToast()` devolve `toast(options)` e `dismiss(id)`.
- Geometria concêntrica: raio `--radius-xl` (24) com padding 12 dá 12 de raio interno, então o botão de ação é `Button size="sm" radius="md"`. Canto nativo declarado direto, como o Tooltip; fora do recorte do fallback porque contém um botão com anel de foco.
- Animação só de `transform` e `opacity`, que o compositor resolve sem layout: entra com `--ease-spring` em `--duration-slow`, sai em `--duration-base`. A saída existe porque `dismiss` primeiro marca `open: false` e só remove 240ms depois. `prefers-reduced-motion` corta as duas.
- Timer por item, com pausa em hover e foco: o efeito começa um `setTimeout` com o tempo restante e, ao pausar, desconta o que passou. Erro (`danger`) não fecha sozinho; os outros fecham em 5s. Escape fecha o toast focado.
- Três visíveis no máximo; o quarto espera na fila e só começa a contar quando aparece. `role="alert"` para erro e atenção, `role="status"` para o resto.
- Canto superior direito no desktop, largura total no topo no mobile com `safe-area-inset-top`. A entrada desce de cima (`translateY` negativo), no sentido de onde o toast vem. Ícone centrado na altura do bloco de texto.

### Paginação

- `Pagination` é controlada: recebe `page`, `pageSize`, `total` e devolve `onPageChange` e `onPageSizeChange`. Quem chama decide se vai para a URL ou para o estado, e volta para a página 1 ao trocar a quantidade. Sem `onPageSizeChange`, o menu de quantidade nem aparece.
- **Uma caixa só, na pegada de uma referência do usuário** (2026-09-08): primeira, anterior, a página em vigor, próxima e última, separadas por fios dentro da caixa. A caixa tem o fio fino da casa (0,6px em `--color-border`), raio `md` com `corner-shape: squircle` declarado direto (contém botões com anel de foco e um dropup que não podem ser cortados), fundo na cor da página e a altura do controle pequeno mais 2px de folga de cada lado. Os fios de dentro são `Separator` vertical vestido pela caixa: mais baixos que ela (a altura do controle menos 12px) e em `--color-border`, porque o `--color-separator` do `Separator` puro, quase três vezes mais opaco, virava grade.
- **A página em vigor lê "1/12"**, só texto em algarismo tabular, `footnote` medium, com largura mínima para a caixa não pulsar ao trocar de página (uma lista para pular direto durou uma rodada e saiu a pedido). O menu de quantidade ("Mostrar 30", só no desktop) se veste como o resto da caixa pelas variáveis do `Listbox`: sem fundo nem fio próprios, altura do controle pequeno. Os botões são `IconButton` fantasmas `sm` com canto `md`, e os das pontas usam o caret duplo. Quem chama decide o que acontece ao trocar de página; a base de clientes leva a coluna de conteúdo de volta ao topo, macio salvo com movimento reduzido, porque o `scroll` do roteador só alcança o documento e na concha quem rola é a coluna.
- A leitura completa ("Página 1 de 12, itens 1 a 24 de 288") fica em texto oculto com `aria-live`; a faixa visível de itens e o indicador em negrito da versão anterior saíram, porque a referência é só a navegação.
- A barra nunca quebra linha (`flex-wrap: nowrap`). Abaixo de 48rem (`MOBILE_QUERY`, por media query em CSS, sem JS) o menu de quantidade some e fica a navegação inteira.
- **No celular a barra não fica na página: ela entra na barra flutuante do menu** (2026-09-09, a pedido). Passando de uma página, a lista pendura anterior, "1/12" e próxima na barra de baixo por `useFloatingPagerRegistration`, no mesmo contrato de salvar e sair de uma janela, e a barra troca de modo pelo mesmo fundido; com uma página só, ela volta a ser busca e sino. Uma janela aberta manda na lista, porque o formulário é o assunto da hora. A grade e a tabela seguem com a barra própria no desktop.

### Barra de rolagem

Desenho único em `globals.css`, valendo em tudo que rola: polegar de 3px em `--color-fill-quaternary` que escurece no hover, com 2px de folga de cada lado e nas pontas (pedido de 2026-09-07: a barra não encosta em borda nenhuma do que rola; a folga sai de uma borda transparente no polegar com `background-clip: padding-box` e de `margin` no trilho, então a barra ocupa 7px de layout), trilho transparente e nenhuma seta nas pontas.

- As duas famílias não convivem. Assim que `scrollbar-width` ou `scrollbar-color` aparecem na regra, o Chrome descarta os pseudo-elementos `::-webkit-scrollbar` e cai na barra nativa, que no Windows vem grossa e com uma seta em cada ponta. Por isso as propriedades padrão ficam dentro de `@supports not selector(::-webkit-scrollbar)`, que só o Firefox atende, e o desenho vive nos pseudo-elementos.
- Pelo mesmo motivo, componente nenhum declara `scrollbar-width: thin` por conta própria: fazer isso desliga o desenho global naquele elemento. Quem quiser esconder a própria barra declara `scrollbar-width: none`, que é o caso do menu.


### Tabela de dados

Dois níveis: os primitivos estáticos em `ui/table` (região que rola, tabela, cabeçalho, linha, célula, em CSS Module) e o `DataTable` em `ui/data-table`, que compõe os primitivos e cuida do que é interação: ordem, marcação com marcar tudo, linha clicável, coluna de ações, densidade, zebra, esqueleto, vazio e pé com contagem e paginação.

- **O cabeçalho é a barra presa no topo da região, no cinza secundário (`--table-head`) e colada na moldura e na primeira linha**: cada `th` fica `sticky` por conta própria, e os fios dele (embaixo e entre as colunas) vão por sombra interna, porque em tabela de bordas fundidas a borda de uma célula presa não acompanha a célula ao rolar. A superfície da região é `--table-surface`, que o `DataTable` veste no fundo da página. Passou por quatro formas em 2026-09-08: colado com fio embaixo, solto com vão e recuo de 8px em duas camadas, junto às linhas mas ainda recuado, e por fim sem recuo nenhum, a pedido ("tire esse padding interno"), com a moldura recortando os cantos.
- **Grade inteira no fio da casa**: fio entre as linhas, fio vertical entre as colunas (`.cell + .cell`) e os mesmos fios no cabeçalho por sombra interna (pedido de 2026-09-08). O canto da região é o `xs`, 4px, discreto (pedido do mesmo dia; era `lg`).
- **A coluna de ações é presa na ponta direita** e sem título à vista (só para o leitor de tela, em `VisuallyHidden`): rolando na horizontal o leque continua à mão. A célula herda a cor da linha, e por isso as cores de linha (superfície, zebra, hover, marcada) são opacas, misturadas sobre `--table-surface` em vez de véus transparentes; os fios da célula presa vão por sombra interna, como no cabeçalho.
- **Zebra é um véu de 3% da tinta do texto** em `:where()`, um degrau abaixo do hover (8%): a linha seguinte sai só um pouco mais escura nos dois temas, e o hover e a marcação continuam mandando. O catálogo liga a zebra.
- **Altura fixa por `fill`**: com a prop, o `DataTable` toma a altura de quem o monta (`height: 100%`, região em `minmax(0, 1fr)` e o pé em linha própria) e rola as linhas por dentro, nos dois eixos. **O que sobra abaixo da última linha vira linhas vazias na mesma grade** (pedido de 2026-09-08, "o espaço em branco preenchido com o design da tabela"): a região é medida por `ResizeObserver` e a cada troca de linhas, e entram quantas linhas de enchimento couberem inteiras na altura de uma linha de verdade, marcadas por `data-filler` e fora da medida, com a zebra e os fios seguindo. O catálogo em tabela põe a prancha em `auto minmax(0, 1fr)` com a altura da tela, então a barra fica em cima, a tabela toma o resto e a paginação está sempre à vista; a grade de cartões segue rolando a página. Para isso a tela do catálogo tem `height: 100%` e trilha `minmax(0, 1fr)`, e não `min-height` (acerto de 2026-09-08): com a altura indefinida a trilha crescia com o conteúdo e a tabela nunca ficava presa.
- **Fio da casa em tudo**: 0,6px em `--color-border` na borda da região, embaixo do cabeçalho e entre linhas. `--color-separator`, a 29%, virava grade.
- **Densidade compacta** é a das listas longas: 6px em cima e embaixo dá linha de 36px com etiqueta pequena dentro, o dobro de linhas por tela; o cabeçalho fica em 8px e caption. O catálogo usa compacta; a padrão continua para tabelas de poucas linhas.
- Célula com valor e complemento (preço com a cobrança, contagem com a aprovação) fica numa linha só, o complemento em caption apagado: duas linhas por célula é o que engorda a linha.
- **O painel do `Listbox` e o do `DatePicker` são de vidro** (2026-09-09, a pedido): a receita das camadas do menu, fundo quase transparente com o borrão desenhando a caixa, fio fino e a sombra grande; na bandeja do celular o calendário usa o vidro da bandeja, que tem mais corpo. A superfície do painel do listbox é a variável `--listbox-panel-bg`, porque lista sobre lista existe: os seletores de mês e ano abrem por cima do vidro do calendário, e a 20% sobre 20% ficavam quase invisíveis, então ali eles recebem o vidro da bandeja. O respiro de cima e de baixo do painel mora na lista que rola, e não no painel, e a busca não desconta margem negativa nenhuma (2026-09-09). **O painel vai para o corpo da página, portado e fixo** (mesma data, e é a causa do painel truncado que aparecia "às vezes"): dentro de uma coluna que rola, como o formulário do orçamento, uma caixa absoluta é recortada pela borda dela, e o painel aparecia cortado dependendo de onde o campo estava na rolagem. Portado, ele nunca é recortado; a posição sai do `useAnchoredPosition` e é reencaixada pela medida real, como no menu da casa, e num campo a largura chega em pixels do próprio campo. O piso de largura passou a ser em rem, e não em porcentagem: no corpo da página, os 100% mediam a tela inteira e a caixa nascia gigante, borrando meia tela com o vidro dela (relato de 2026-09-09). O toque fora e a fila de camadas passaram a ser os hooks da casa (`useOutsideDismiss`, `useLayer`), então a caixa aberta dentro de uma janela responde antes dela.
- **No celular, `Listbox`, `Select` e `DatePicker` abrem na bandeja do `Dialog`** (2026-09-10, a pedido: todo seletor abre a bandeja de baixo, o componente que a casa já tem), na receita do menu de opções: vidro da bandeja, sem escurecimento, sem roubar o foco (o teclado não sobe), com a busca presa no topo, as linhas na medida de toque e o respiro padrão das bandejas, mais a folga da barra flutuante embaixo quando uma janela com ações está aberta por baixo. Fora da bandeja o `Listbox` desliga a própria fila de camadas e o fechamento por toque fora, porque quem cuida disso passa a ser o `Dialog`. O `DatePicker` tinha uma bandeja própria, e ela nascia na camada da janela abaixo do próprio fundo escuro, que estava na camada das caixas flutuantes: o calendário aparecia apagado atrás de um véu, sem dar para tocar (relato de 2026-09-10). A bandeja própria saiu; dentro do `Dialog` o calendário fica centrado na largura em que desenha bem, e os seletores de mês e ano abrem outra bandeja por cima, pela fila de camadas. A `HoverCard` ganhou `scheme` para desenhar no tema de uma superfície de tema fixo: portada para o corpo da página ela herdava o tema de lá, e o vidro escuro sobre o documento sempre claro virava um borrão cinza.
- **O `Field` não apaga mais o adorno da ponta de quem o monta** (acerto de 2026-09-09): com erro ele troca o `iconEnd` pelo "?" da mensagem; sem erro, o que o controle já trazia fica, que é o que faz o informativo das parcelas do orçamento aparecer dentro do campo.
- **Máscara `integerPercent`** (`lib/masks.ts`, 2026-09-09): número inteiro com o "%" dentro do valor escrito, e não num afixo ao lado do campo, para o sinal ficar colado no número. É a dos campos de desconto do orçamento.
- `AnimatedNumber` e `AnimatedMoney` (`components/ui/animated-number/`, 2026-09-09) contam do valor antigo até o novo em `requestAnimationFrame`, em 420ms com a curva de saída da casa: mexer na quantidade faz o total caminhar em vez de pular. Com movimento reduzido, e no primeiro desenho, o valor entra direto. É Client Component, mas um Server Component pode montá-lo, porque o servidor desenha o valor final; os totais do documento de orçamento usam.
- O `Listbox` (e o `Select` sobre ele) aceita **item ilustrado e busca no painel** desde 2026-09-09: `media` põe a foto, a bolinha ou a arte à esquerda, `caption` põe a segunda linha apagada (e **o gatilho repete a linha do item escolhido**, com foto e legenda, quando ele as tem: o campo mostra o cliente, e não só o nome dele; nesse modo a altura do gatilho fica livre, o recuo da esquerda encurta quando há foto e o texto alinha ao começo, porque num `button` o navegador centraliza), `searchable` prende um campo de busca no topo do painel (filtra rótulo e legenda pelo `slugify`, sem acento, como as listas da casa), `visibleLimit` mostra só os primeiros N até alguém buscar (com o item em vigor sempre entre eles, e um aviso no pé dizendo entre quantas opções a busca corre) e `emptyLabel` é o que a lista diz quando nada bate. **Dentro de um campo de formulário o painel tem a largura do campo**: em `max-content` ele passava da moldura e lia como formulário quebrado. O foco ao abrir vai para a busca no ponteiro fino e para a lista no toque, que é a regra do seletor de equipe: no dedo, focar o campo abriria o teclado por cima da lista. Os algarismos tabulares saíram do item, pela decisão do dia anterior.
- `DataTableEmptyValue` é a etiqueta neutra pequena "Não condiz", para campo sem nada (item sem orçamento), decisão de 2026-09-08: dito em palavras e na mesma peça em toda tabela, a coluna não parece quebrada. O ponto apagado e a versão em texto solto duraram uma rodada cada. Fato que existe mas sem número tem palavra própria em etiqueta, como o prazo "Indeterminado" e o estoque "∞/∞" do catálogo.
- **O glifo de ordem é sempre o chevron duplo** (`CaretUpDownIcon`, o mesmo dos seletores da casa), na coluna ativa e nas outras: a ativa só troca de tinta, e a direção fica em `aria-sort`. As setas para cima e para baixo destoavam do resto da tela (pedido de 2026-09-08).
- **Sem dica de interrogação no cabeçalho** (decisão de 2026-09-08): a coluna `hint` e o (i) com `Tooltip` saíram; o nome da coluna basta, e o que precisar de explicação vai para a ficha.
- **Situação sem ponto**: `DataTableStatus` é a `Badge` pequena e nada mais, pela regra da etiqueta (não existe variante com ponto colorido). A primeira versão, com um `CircleIcon` reduzido, durou uma rodada.
- **Números na fonte padrão, nunca tabulares** (decisão de 2026-09-08, para o catálogo, a base de clientes e os ajudantes da tabela): o `numeric` do `Text` saiu de todas as células, contagens e fichas dessas telas, e a célula alinhada à direita só alinha. O `numeric` continua existindo no `Text` para quem precisar em outro lugar.
- **Nome e dinheiro em footnote**: `DataTableTitle` (nome em medium, legenda em caption) e `DataTableMoney` (semibold, algarismos tabulares) desceram de subheadline para footnote, a pedido de 2026-09-08, para a linha compacta caber mais e a tabela não gritar.
- **A marcação é a `Checkbox` da casa, que marcada vai para o escuro** (`--color-label`, o preenchimento da dica), e não para a cor da marca, decisão de 2026-09-08 que vale para toda caixa de marcar: é controle de lista, não ação.


### Cantos

- Todo canto arredondado passa pelo sistema de cantos da casa, sem lib. `squircle("lg")` de `src/lib/corners.ts` emite `data-squircle` e `data-squircle-radius`; `squircleAuto()` emite só `data-squircle` e deixa o raio para o CSS; `squirclePx(n)` para raio fixo fora da escala. `border-radius` continua sempre no CSS: é o fallback e é o que o motor lê quando o raio não vem no atributo.
- Onde existe `corner-shape` (Chromium 139+), `globals.css` aplica `corner-shape: squircle` em `[data-squircle]` e acabou: fundo, borda, sombra, anel de foco e recorte de filhos saem do motor do navegador, sem JS. O motor detecta o suporte com `CSS.supports` e não liga nada.
- Sem `corner-shape` (Safari, Firefox), o motor em `src/lib/squircle/` recorta por `clip-path: path()` com a superelipse (suavização 0,6, a do iOS, pelo algoritmo de cantos suavizados do Figma em `path.ts`). Só recorta quem já recorta (`overflow: hidden` ou `clip`) ou quem pede com `{ clip: true }`. Tudo o mais fica no `round` do `border-radius`. Motivo: recorte cortaria anel de foco de botão e popover que sai do container, que foram exatamente os bugs do cornerKit.
- Elemento com borda nunca é recortado: a borda CSS segue o arco de círculo e o recorte seguiria a superelipse, então ela apareceria quebrada no canto. É por isso que nenhuma variante do fallback desenha borda; borda é sempre CSS.
- Motor (`engine.ts`): um `ResizeObserver` só para todos os elementos, escrita agrupada por `requestAnimationFrame`, cache de caminhos por tamanho e raio, `MutationObserver` para elemento que entra, sai ou troca de atributo, `WeakMap` para o que já foi aplicado. Escrever `clip-path` não muda layout, então não realimenta o observer: sem loop por construção. Nada de `<style>` injetado, então a CSP fica em paz. `SquircleProvider` no layout raiz só liga o motor uma vez.
- Componente client com raio dinâmico usa `useSquircle(raio, clip)` de `src/lib/squircle/use-squircle.ts`, que devolve um ref callback: emite os atributos e registra o elemento, com limpeza ao desmontar.
- Quem declara `corner-shape: squircle` direto no CSS, sem `data-squircle` (FieldShell, Tooltip, Listbox, Pagination, Checkbox, Toast), fica nativo no Chromium e redondo no fallback, de propósito: são elementos com anel de foco, popover ou conteúdo que não pode ser recortado.
- O cornerKit saiu em 2026-08-29 depois de uma sequência de bugs: `<style>` injetado bloqueado pela CSP, fundo repintado por SVG que atrasava e piscava, caixa de 20px do Checkbox virando invisível, borda semitransparente empilhando alfa, um observer por elemento. O nativo cobre o caso principal e o fallback nosso é pequeno, previsível e sem borda.
- Escala em passos de 4px para o encaixe concêntrico: xs 4, sm 8, md 12, lg 16, xl 20, 2xl 28. A regra da Apple é raio interno igual ao externo menos o padding, e nessa escala a conta sempre cai em outro token (20 menos 8 dá 12, 16 menos 4 dá 12).
- **Canto de dentro é sempre concêntrico.** Nada aninhado escolhe raio próprio: ele sai do raio do pai menos o padding que os separa. No CSS é `calc(var(--corner) - var(--pad))`, no TS é `concentric(raioDoPai, espacamento)` de `src/lib/corners.ts`. Quando os dois convivem, o mesmo número alimenta o `border-radius` e o `data-squircle-radius`, senão o fallback e o desenho do cornerKit discordam.
- Botão é o exemplo da casa: raio 20 no tamanho `md` e `padding-block` de 8 dão etiqueta interna de 12, que é outro token da escala. É por isso que a escala anda de 4 em 4.
- Botão só de ícone tem escala própria (`--icon-button-radius-*` e `iconButtonCornerRadius`), com o raio em exatamente metade do lado: 18 em 36, 22 em 44, 26 em 52. É o máximo que a superelipse aceita antes do clamp, e dá o formato de ícone do iOS. Passar disso não arredonda mais, só faz o CSS e o cornerKit divergirem.
- Nesse botão o lado é fixo (`width` e `height`, não `min-`), o padding é zero e o glifo é 45% da altura por `calc`, então a proporção do ícone é idêntica nos três tamanhos.

### Containers aninhados

- `Surface` é o container da casa. Empilhe à vontade: a profundidade sozinha define raio e padding, por seletor descendente no CSS Module. Ninguém passa nível nem faz conta no ponto de uso.

| nível | raio | padding | raio interno |
| --- | --- | --- | --- |
| 1 | 40 | 16 | 24 |
| 2 | 24 | 12 | 12 |
| 3 | 12 | 8 | 4 |
| 4 e além | 4 | 8 | 4 |

- A escada é concêntrica de verdade, não aproximação: em toda linha o raio interno é o externo menos o padding, e o resultado cai sempre num token existente. Só fecha assim por causa dos valores da escala (4, 8, 12, 20, 24, 32); mexer num deles quebra a corrente.
- O raio interno é o externo **menos** o padding, nunca mais. O arco do pai tem centro em (R, R); o filho recuado por P tem centro em (P + Ri, P + Ri). Para os centros baterem, Ri = R − P. Somar o padding empurra o centro do filho para dentro e desalinha: com pai 24 e padding 16, somar erra o centro em 32px.
- Por isso padding folgado se resolve **subindo o raio do pai**, não o do filho. O nível 1 usa `--radius-3xl` (40) justamente para caber 16 de padding e ainda sobrar 24 de raio interno.
- `Surface` não declara `data-squircle-radius`. No fallback o motor lê o `border-radius` computado. Assim o CSS continua sendo a fonte única do raio e a escada funciona em qualquer profundidade sem duplicar número em TS.
- Quem precisa de raio fixo e conhecido (Button, Table, Kbd) continua declarando o atributo, que tem prioridade sobre a leitura.

Junto, **a tela do menu entrou na fila de camadas** (`useLayer`), como janela, bandeja e caixa colada no gatilho: aberta por cima de um formulário, é ela quem responde ao Escape, que antes fechava a janela por baixo dela. Descer as janelas para baixo da barra foi tentado por uma rodada em 2026-09-08 e saiu a pedido. O provedor vive na `AppFrame`; a janela registra a cada render e o provedor guarda as funções numa referência e só muda estado quando o que se desenha muda (rótulo, espera), para o menu não re-renderizar a cada tecla digitada. Menu aberto continua recolhendo o grupo até sobrar o X. **Regra para o conteúdo nessa situação** (2026-09-08): a folga fica **dentro do que rola**, abaixo do último item, e nunca na moldura da janela, porque na moldura ela virava uma faixa vazia à vista em toda bandeja curta. A medida é o token `--floating-bar-inset` (a altura da barra mais o recuo, um respiro e a área segura). Quem abre com ações na barra dá essa folga ao próprio corpo no celular (a ficha do cliente e criar equipe), e o menu de opções que abre por cima lê a marca `data-floating-actions` que o provedor põe no `html` e dá a folga à própria lista, então o menu de situação da ficha fecha acima da barra. Uma versão que pôs a folga na moldura de toda bandeja durou uma rodada e saiu a pedido. **A troca de modo é um fundido de verdade**: os modos ficam montados um sobre o outro e o que sai desbota e encolhe um fio enquanto o que entra aparece, com a curva que assenta, só em `opacity` e `transform`; o apagado fica `inert`. **Quem mede a barra é só o modo em vigor** (acerto de 2026-09-10): o apagado sai do fluxo, em posição absoluta, então a largura é a do que está à vista. Os três dividiam uma cela de grade e a caixa ficava do tamanho do maior, o que servia enquanto eles tinham medidas parecidas; com uma ação a mais no modo de janela, a barra da lista voltava do editor larga demais, com um vão vazio ao lado da busca (relato de 2026-09-10). O último modo de ações fica guardado para o fundido de saída ter o que desenhar, e o modo de ações existe desde o começo, apagado e inerte, com um rótulo de espera, senão ele montava já no estado final e entrava sem fundido (remontar o conteúdo, a versão anterior, piscava). **A gaveta de criar equipe segue a mesma dinâmica** (2026-09-08): registra criar e sair enquanto está aberta (com criar desligado até o formulário estar preenchido, pelo `disabled` das ações), some com o rodapé no celular e liga o escurecimento ali. Toda janela de criar ou editar da casa entra nesse contrato.

### Movimento das camadas

Toda camada flutuante da casa entra e sai animando, e a receita mora em dois lugares só: `usePresence` em `hooks/use-presence.ts` e `layerMotion` em `components/ui/styles.ts`.

- **Curva por tipo de movimento** (2026-09-08). O que percorre distância usa `--ease-settle` (`cubic-bezier(0.22, 1, 0.36, 1)`): sai rápido e chega devagar, sem passar do ponto. É o que dá sensação de sistema em vez de site, porque a velocidade que a pessoa sente vem do começo do movimento, e não da duração total; a cauda longa é o que faz parecer macio. Por isso a duração pode ser generosa sem ficar lenta, e nasceu o `--duration-glide` (420ms) para o movimento principal. `--ease-standard` fica com troca de cor e de fundo, que não percorrem espaço, e `--ease-spring` segue no gênio das caixas coladas no gatilho, onde o pequeno exagero é o efeito. A regra veio de a barra do celular ter ficado rápida demais e seca quando as animações dela deixaram de animar layout.
- **Saída sempre mais curta que a entrada, mas com corpo.** Quem fecha já decidiu, e segurar a camada no caminho de volta é o que faz interface parecer lenta; só que curta demais lê como seca (relato de 2026-09-08). Entrada em `--duration-glide`, saída de gaveta e bandeja em `--duration-slow` (320) e das caixas coladas no gatilho e da janela centrada em `--duration-base` (200), sempre com `--ease-leave` (`cubic-bezier(0.4, 0, 0.2, 1)`), e a bandeja descendo inteira, sem desbotar (com opacidade junto ela sumia no meio do caminho e lia como corte; quem desbota é o fundo): a curva que assenta, usada na entrada, gasta quase todo o movimento no primeiro quarto do tempo, e na saída isso é a camada sumindo de repente. O fundo desbota no mesmo tempo da janela, senão ela ficava solta sobre a página no fim. O teto de espera do `usePresence` subiu para 480ms, acima da saída mais longa.
- **Peças que se movem juntas ganham durações diferentes, e não atrasos.** Na barra do celular são três (420 no deslocamento, 320 no vidro, 200 no grupo): partindo no mesmo instante, o grupo some primeiro, o vidro troca em seguida e o deslocamento ainda está pousando. Lê como coreografia sem `animation-delay` em lugar nenhum, que é uma coisa a menos para sair de sincronia.

- Fechar por toque fora é `useOutsideDismiss` em `hooks/use-outside-dismiss.ts`, o mesmo nas caixas coladas no gatilho (troca de time, notificações, opções da conta) e no `Dialog` sem escurecimento (decisão de 2026-09-05): apontar fora fecha a camada e engole o clique que vem em seguida, porque quem clica fora quer só fechar, e antes o botão que estava embaixo do ponteiro disparava junto. O ouvinte do clique entra na captura do documento, antes do React, e sai sozinho depois do pointerup, então um toque sem clique não deixa nada engolido para trás.

- `usePresence(open)` devolve `present`, `state` e `onAnimationEnd`. `open` é a intenção; `present` é se a camada ainda existe na tela; `state` vai para `data-state` e é o que o CSS lê para escolher entre entrar e sair. A camada fica montada até o `animationend` da saída, com um temporizador de segurança caso ele não chegue. O ajuste de `present` ao abrir é feito durante o render, o padrão que o React recomenda para reagir a prop nova, e não em efeito, que o lint barra.
- `onAnimationEnd` vai só no elemento animado e ignora o que subiu dos filhos: o evento de animação borbulha, e um giro ou um badge lá dentro fechava a camada antes da hora.
- `layerMotion` é o gênio da lâmpada na versão que o CSS alcança: a caixa nasce a 90% e um degrau mais perto de quem a abriu (`--genie-x` e `--genie-y` dizem de onde) e cresce até o lugar com a mola curta da casa; ao fechar volta pelo mesmo caminho, mais rápido e sem mola, porque saída não pede atenção. Com movimento reduzido sobra só o fade: a regra é sobre deslocamento, e opacidade não desloca nada.
- Cada moldura tem o seu caminho: as caixas coladas no gatilho usam o gênio com a origem no lado do gatilho; a janela centralizada nasce um degrau abaixo e sobe; a gaveta lateral entra e sai deslizando pela lateral; a bandeja do celular sobe do rodapé e volta para ele; a tela cheia do menu sobe um degrau e desbota. Fundo que escurece e véu leve fazem fade nos dois sentidos.
- Quem monta uma camada com `Dialog` precisa mantê-la montada enquanto `open` é falso, senão a saída não acontece. A busca, que era montada só ao abrir, passou a ficar sempre montada com uma chave que muda a cada abertura: a chave remonta o conteúdo, então o estado nasce limpo sem escrever estado em efeito, e o cookie das recentes é lido só quando há documento, porque agora ela também renderiza no servidor.
- Troca de seleção dentro das camadas também anda: o traço da aba de notificações cresce a partir da esquerda, a lista troca com um fade curto quando a aba muda, a opção de tema desliza cor e sombra, e as linhas de lista já transitavam o fundo.

### Hover dos controles

No toque não há hover nem anel de foco (decisão de 2026-09-07): toda regra `:hover` e `:focus-visible` da casa vive dentro de `@media (hover: hover)`, que só vale onde há ponteiro de verdade, então no celular sobra só o `:active`. Foi um pedido do usuário e é um desvio consciente da regra de foco visível, restrito a aparelhos sem ponteiro fino; um teclado ligado a um celular perde o anel. Quem escrever hover ou foco novo segue a mesma receita.

Receita única em `hoverMotion` (`components/ui/styles.ts`), aplicada ao `Button` e a toda linha, pílula, aba e opção das camadas do menu; as linhas do menu em CSS Module repetem a mesma receita, porque módulo não importa mixin do Emotion.

- A transição é assimétrica de propósito: entrar no hover leva o tempo base, para a cor chegar macia, e sair leva o tempo curto, para o ponteiro que passa por uma lista não deixar rastro. A duração maior mora na regra `:hover`, então ela só vale na ida.
- Fundo, cor, borda, sombra e opacidade transitam juntos. Antes só o fundo transitava e a cor do rótulo saltava por cima dele.
- O clique afunda um fio (`scale(0.985)`, 60ms) e volta, o retorno tátil que o Mac dá. Desabilitado não afunda.


### Janela (Dialog)

Moldura da casa para conteúdo que interrompe: caixa centralizada no desktop e bandeja subindo do rodapé abaixo de 48rem, na mesma decisão do `DatePicker`. Portal em `document.body`, `role="dialog"`, Escape fecha, o Tab dá a volta por dentro da caixa e o foco volta para quem abriu. Rolagem trava enquanto está aberta e `prefers-reduced-motion` corta a animação.

- **A trava de rolagem pega a coluna, e não o documento, e só quando a janela bloqueia** (correção de 2026-09-08, sobre um relato de que às vezes o celular saltava para o topo ao abrir uma janela). Na concha da aplicação o documento nunca rola: `.shell` tem `height: 100dvh` e quem tem `overflow-y: auto` é a coluna de conteúdo. A `Dialog` e o `DatePicker` declaravam `overflow: hidden` no `html`, o que não travava nada e ainda causava o pulo: no Safari do iPhone a rolagem do documento é a mesma que o navegador usa para esconder a barra de endereço, então travá-la com a barra recolhida faz o Safari trazer a barra de volta e zerar o deslocamento, o que aparece como a página saltando. Era intermitente porque dependia de a barra estar recolhida. Trocar `overflow` de um elemento que rola por dentro não mexe no `scrollTop` dele nem no visor. A coluna se marca com `data-scroll-container` (`lib/scroll.ts`), `useScrollLock` (`hooks/use-scroll-lock.ts`) trava quem estiver marcado e cai no documento nas telas sem a concha, e a contagem é compartilhada porque camada abre de dentro de camada: só a primeira trava e só a última destrava. **O gesto também é barrado** (2026-09-08, depois de a página atrás rolar quando o dedo passava do fim do conteúdo da janela): enquanto há trava, todo `touchmove` e `wheel` do documento é impedido, salvo quando nasce dentro de algo que rola de verdade, que é o corpo da própria janela; e o painel da `Dialog` leva `overscroll-behavior: contain`, para a rolagem de dentro não encadear ao chegar no fim. Com janela aberta, a tela atrás não rola de jeito nenhum. A trava só entra com escurecimento ou na bandeja do celular: gaveta avulsa no desktop deixa a página viva atrás dela, senão a tela inteira parecia travada ao abrir a ficha do cliente (relato do mesmo dia).
- A constante do atributo mora em `lib/scroll.ts`, e não junto do hook: a concha é Server Component e o hook é de cliente, e **constante importada de um módulo `"use client"` chega ao servidor como referência de cliente, não como o valor**. O atributo simplesmente não saía no HTML, sem erro nenhum. Vale para qualquer constante compartilhada entre os dois lados.

- A bandeja do celular sempre põe alguma coisa atrás de si: o escurecimento cheio quando a janela bloqueia o resto, e um véu leve (`--color-scrim-soft`) quando ela é avulsa. Sem nada atrás, a bandeja lia como parte da página. No desktop, dispensar o escurecimento continua deixando a tela limpa.
- Janela de vidro carrega a própria escuridão: ela vai para a sombra do painel, sem desfoque e com espalhamento de `100vmax`, que cobre tudo em volta e nada atrás do vidro, e o fundo fica transparente só para pegar o clique. Pintada no fundo, atrás do vidro, o borrão a puxava para dentro e a bandeja inteira escurecia junto, lendo como se o véu estivesse por cima dela. Subir e descer também desbotam, porque a escuridão agora anda com a bandeja e precisa sumir com ela.
- **Toda janela bloqueia a página atrás** (decisão de 2026-09-08, a pedido: com uma janela aberta, a tela de trás nunca responde). O fundo existe sempre e é quem fecha ao toque fora, só quando a janela era a camada de cima no começo do toque; toda janela é `aria-modal` e trava a rolagem. `scrim` decide só o peso: com ele (o padrão) o fundo escurece em `--color-scrim`; sem ele o fundo é transparente no desktop, deixando a página à vista sem deixar tocar, e véu leve na bandeja do celular. O `useOutsideDismiss` saiu da `Dialog` (segue nas caixas coladas no gatilho), porque o fundo cobre o caso.
- Canto declarado direto no CSS, sem `data-squircle`: a janela guarda foco e conteúdo que sai do fluxo, e o recorte do fallback cortaria o anel de foco de quem está dentro. Mesma escolha do `Listbox` e do `Tooltip`.
- Tamanhos por `data-size`: `sm` 24rem, `md` 30rem, `lg` 40rem. A altura é limitada por `min(34rem, 100dvh menos 4rem)` no desktop e 85dvh na bandeja, e quem rola é o conteúdo de dentro, nunca a página.
- **Fila de camadas** (`hooks/use-layer.ts`, 2026-09-08): janela, gaveta, bandeja e caixa colada no gatilho entram todas numa pilha só, porque uma abre de dentro da outra. `useLayer(aberta)` registra e `isTopLayer(id)` diz quem responde. A `Dialog` só atende Escape quando é a de cima, e o `DropdownMenu` registra o popover do desktop; no celular quem registra é a bandeja dele, que já é `Dialog`. Antes a pilha era local da `Dialog` e o popover não existia nela, então com o menu de opções aberto por dentro do perfil do cliente o Escape fechava os dois.
- **Fundo só fecha o que a pessoa mirou**: a janela guarda, no `pointerdown`, se era a camada de cima naquele instante, e o clique no fundo só fecha se era. É o que separa uma camada da outra no toque: tocar fora do menu de opções fecha o menu, e o perfil embaixo fica de pé, porque quando o dedo desceu quem mandava era o menu. O engolidor de clique do `useOutsideDismiss` continua, mas deixou de ser a única garantia, que dependia de ordem de propagação e de qual elemento estava sob o dedo depois do toque. **O toque fora também só fecha a camada de cima** (2026-09-08, depois de fechar o menu de opções por fora derrubar a gaveta atrás dele): o `useOutsideDismiss` ganhou um quarto argumento, `when`, e a `Dialog` sem escurecimento passa `isTopLayer`; quando não é a de cima, nem fecha nem engole o clique, então o item do menu que estava sob o dedo dispara normalmente.
- **Arrastar a alça fecha a bandeja** (2026-09-08, a pedido): segurar na barrinha do topo e puxar para baixo leva o painel junto por `translate` inline, escrito uma vez por quadro dentro de `requestAnimationFrame`. São duas escolhas de fluidez, feitas no mesmo dia depois de o arrasto sair travado: `translate` e `transform` são propriedades independentes, e as animações de entrada e de saída da bandeja andam em `transform`, então escrever numa não disputa com a outra nem obriga o navegador a resolver de novo, a cada quadro, o quadro-chave implícito da animação que segura o painel no lugar; e o ponteiro dispara bem mais de sessenta eventos por segundo, então agrupar a escrita num quadro corta recálculo de estilo que a tela nem chegaria a mostrar. O painel também ganha `will-change: translate` enquanto o dedo está nele, porque a bandeja de vidro carrega borrão e uma sombra do tamanho da tela, e sem a promoção a camada própria o navegador repintaria os dois a cada quadro. Soltando além de um terço da altura, com teto de 120px, a janela fecha e a animação de saída continua de onde o dedo largou, em vez de saltar para o lugar antes de descer; aquém disso ela volta com a transição curta da casa. A alça desenha 4px, mas quem pega o dedo é a área invisível em volta, na medida de toque da casa, e ela declara `touch-action: none` para o navegador não rolar a página no meio do gesto. Continua `aria-hidden`: é atalho de gesto, e Escape, o X e o fundo já fecham.
- `focusOnOpen={false}` para o foco no próprio painel, e não no primeiro campo: no celular focar um campo faz o teclado subir sozinho e comer metade da bandeja antes de a pessoa ver o conteúdo. O Tab continua preso dentro da janela, porque o painel carrega `tabindex="-1"`. A prop não se chama `autoFocus` porque o lint barra esse nome em JSX.
- Janela e gaveta usam o mesmo canto, o raio `3xl`, porque são a mesma família e destoavam quando a centralizada ficava num raio menor. A bandeja continua no `xl`, que é o degrau da casa numa tela estreita.
- `placement="end"` troca a caixa centralizada por gaveta na lateral final, entrando por `translateX`, com 8px de folga nos quatro lados (o recuo mora na moldura) e canto completo, porque ela não encosta em borda nenhuma. No celular a bandeja continua ganhando, porque a regra dela vem depois e vence no que declara.
- **Vidro só nas janelas leves** (a pedido, 2026-09-08): gaveta lateral (`placement="end"`) e janela `lg` saem sempre sólidas, mesmo pedindo `surface="glass"`, porque borrar uma área enorme da tela a cada quadro pesava a página inteira no celular e em máquina fraca; a `Dialog` decide sozinha e quem chama não precisa saber. O vidro fica com as janelas `sm` e `md` e as bandejas dos menus, que borram pouco. Na prática a ficha do cliente, criar equipe, personalizar painel, os perfis abertos pelos blocos e o anexo ficaram sólidos; menus, troca de time, notificações, busca e uso da IA seguem de vidro.
- **`surface="page"`** (2026-09-08, a pedido) usa o fundo da própria página, `--color-bg`, no lugar do cinza elevado do sólido: é a superfície das gavetas laterais, que são extensão da tela e não uma caixa sobre ela, e no escuro o cinza destoava. Passa sempre, também nas janelas pesadas; só o fio marca a borda. As duas gavetas da casa, a do cliente e a do item do catálogo, usam ela.
- `surface="glass"` troca a superfície opaca pelo vidro. Há duas receitas em token: `--glass-bg` e `--glass-blur` (fundo a 0% e `blur(12px)`) são as do painel do login e da barra flutuante, que têm pouco conteúdo e podem ser quase invisíveis; `--glass-layer-bg` e `--glass-layer-blur` (fundo a 20% e `blur(16px)`) são as das camadas com lista e texto por cima, que é o que a janela e os popovers usam, para o que passa atrás não competir com o que está escrito.

### Troca de time

A seta dupla no topo do menu abre uma caixa com busca, os times da pessoa e o convite de criar no rodapé, no formato da referência (a troca de projeto da Vercel).

- Sem escurecer a tela e colada na origem (decisão de 2026-09-03): no desktop é caixa avulsa de 20rem medida a partir do próprio seletor, alinhada pelo início dele, virando para cima quando falta espaço embaixo e acompanhando rolagem e redimensionamento. A medida sai de `useLayoutEffect`, e não de `useEffect`, senão a caixa pinta no canto e pula para o lugar no quadro seguinte. No celular ela vira a bandeja do `Dialog` com `scrim={false}`, porque lá o topo do painel fica longe do polegar.
- A faixa dos times tem altura reservada, de 10rem a 15rem no desktop e até 22rem na bandeja, e é ela que rola. Sem piso, um time só deixava a caixa espremida entre a busca e o rodapé; sem teto, muitos times empurravam o convite de criar para fora da vista.

- Regra no banco: `set_current_org` já existia, é `security definer` e recusa organização de que a pessoa não participa. A web chama por `switchTeamAction` e o aplicativo por `PUT /api/v1/organizacoes/atual`, os dois pela mesma função, então a validação não é repetida em código.
- A lista sai de `listTeams`, que entra pela associação (`organization_members`) e não por `organizations`: a policy de select de lá também deixa passar o time que a pessoa criou, então quem saiu do time continuaria vendo um destino que a troca recusa. O plano de cada linha vem de uma leitura em lote de `organization_subscriptions` com os status de `grantingStatuses`, a mesma lista de `organization_plan`. O aplicativo lê em `GET /api/v1/organizacoes/minhas`.
- O foco fica no campo de busca o tempo todo: as setas movem o item ativo, Enter escolhe e o leitor de tela acompanha por `aria-activedescendant`, então as linhas são `role="option"` e não botões. A busca compara por `slugify` dos dois lados, então acento e maiúscula não atrapalham.
- Escolher um time chama a action, mostra giro na própria linha e refaz a árvore do servidor com `router.refresh()`. Enquanto a troca corre a janela não fecha, nem por Escape.
- A caixa é de vidro nos dois formatos, na mesma receita do painel do login: `--glass-bg` e `--glass-blur`.
- O convite de criar não encosta na borda do rodapé: o recuo é o mesmo da lista, então o hover pinta uma caixa arredondada por dentro, no ritmo das opções de cima, em vez de uma faixa de ponta a ponta.
- Criar equipe fecha a caixa e abre a gaveta de criação, descrita abaixo.

### Busca (CommandPalette)

O campo de busca do menu e o "Buscar" da barra flutuante abrem a mesma janela: campo em cima, atalhos em pílula, o que foi aberto por último e sugestões. Caixa de vidro `md`, centralizada no desktop e bandeja no celular.

- As opções saem de `nav.ts`, que já é a fonte única do menu e tem `href` tipado por rota, então a busca nunca oferece página que não existe. `navLinks()` achata as pastas e carrega o nome de onde a página mora, porque "Acompanhar" e "Visão geral" não dizem nada fora da gaveta; `navHighlights` é o punhado que vira pílula, com rótulo próprio.
- A pílula tinge pela mesma receita do Badge: tinta no matiz a 70% do rótulo e fundo no matiz em alfa baixo, mais forte no escuro, com o contraste já conferido nas 19 cores da paleta. O matiz de cada atalho fica em `navHighlights`, e o ícone herda a tinta em vez de puxar para o cinza. Canto pelo sistema da casa, no raio `md`, e não pílula redonda.
- A fila de atalhos rola na horizontal com a barra de `thinScrollbar`, e não escondida: a régua diz que a fila continua. Quebrar em duas linhas empurrava a lista para fora da vista numa tela estreita. O recuo dela é o mesmo da linha da lista, senão as duas faixas começam em pontos diferentes.
- As duas áreas que rolam desbotam nas pontas por `mask-image`, e não por uma faixa de cor por cima: o painel é de vidro, e um gradiente sólido viraria mancha em vez de sumiço. Em cima a faixa tem o tamanho do recuo, então cai sobre o vão; embaixo ela é maior, porque ali a lista encosta na régua de teclas e o corte seco aparecia inteiro.
- A pílula fica em 36px no toque, e não no alvo cheio: ela é atalho secundário, a lista logo abaixo é quem guarda os 44px da regra, e com 44 aqui a faixa do topo comia um terço da bandeja.
- Cada linha da lista é ícone, rótulo e a seção em etiqueta colorida na outra ponta. Sem seta de abrir no fim: a janela inteira já é uma lista de coisas que abrem, e o ícone repetido em toda linha só somava ruído.
- O matiz da etiqueta é o da seção, declarado em `nav.ts` na pasta e no grupo e propagado por `navLinks()`. Cor de seção mora onde a seção nasce, e não numa tabela paralela que envelhece quando o menu muda.
- A linha da lista tem a altura do menu, 36px com 4px de recuo, e volta ao alvo de toque em ponteiro grosso. Entre um grupo e outro corre a mesma linha que separa os grupos do menu, sangrando o recuo da lista.
- A régua de teclas no pé diz o que dá para fazer daqui: fechar, navegar e abrir. Ela e as próprias teclas somem no celular.
- O rótulo de grupo recua o mesmo que a opção. Ele mora dentro da lista, que já abre o recuo lateral, então o recuo cheio somava duas vezes e jogava "Recentes" e "Sugestões" para dentro.
- Com o campo vazio a janela mostra Recentes e Sugestões; com texto, uma lista só de Resultados, filtrada por `slugify` no rótulo e na seção, então acento e maiúscula não atrapalham.
- Recentes são as três últimas rotas abertas pela busca, em cookie (`sp-recent`), porque Web Storage é proibido pelo lint. Guarda só a rota, que já é pública e conhecida pelo menu, nunca o que foi digitado.
- Um `listbox` só, com o rótulo de cada grupo como item de apresentação dentro dele: um listbox por seção duplicaria o id que o campo aponta em `aria-controls`. O foco fica no campo, a seta move o item ativo e o leitor de tela acompanha por `aria-activedescendant`.
- Quem abre monta o componente, e não o mantém montado com `open={false}`: assim o estado nasce limpo a cada abertura e o cookie é lido uma vez, sem escrever estado dentro de efeito.
- O botão de busca no menu mostra o atalho inteiro, modificador e letra, e não só a letra. O rótulo do modificador vem de `useCommandKey`, que responde Ctrl no servidor e troca para ⌘ na hidratação em Mac, então a marcação não discorda. O atalho é o comando mais a tecla que o campo mostra. Ele toma o lugar da busca do navegador de propósito: procurar no texto da página não serve a quem quer pular para outra tela. A régua de teclas e a própria tecla somem no celular.

### Opções da conta

O chevron duplo do perfil abre a lista colada nele, que sobe porque o perfil mora no rodapé do menu: quem é você em cima, as telas da conta no meio, o tema e a saída embaixo. Vidro, fio da casa e a mesma linha do menu, na mesma altura e no mesmo tom, porque a camada é continuação dele.

- Assinatura leva o chip do plano em vigor, o mesmo rótulo curto que o topo do menu mostra.
- Tema em dois estados na própria linha, sol para o claro e lua para o escuro, com a fila na frente do rótulo como no celular. O apertado é o que tem fundo, sombra e o glifo preenchido; o nome de cada um fica em `aria-label` e em `title`, e o rótulo da linha usa o meio círculo para não repetir a lua. "Sistema" saiu: o produto é escuro por padrão e não segue o aparelho, então a terceira opção só confundia e estourava a linha estreita do celular. O estado do seletor nasce do que o html carrega, e não do cookie, porque sem cookie o produto é escuro. A troca chama `applyTheme`, que saiu do `ThemeToggle` de homologação para `lib/theme.ts` quando os dois passaram a precisar dela.
- Sair é `<a>` cru, e não `Link`: limpar o cookie de sessão exige uma ida ao servidor, coisa que navegação de cliente não faz.
- O painel só existe no desktop, mas as opções são as mesmas nos dois: `accountLinks` e `ThemePicker` saem daqui e a tela cheia do celular monta as mesmas linhas com o CSS dela. As molduras diferem, a lista não, então nenhuma das duas conta uma história diferente da outra.

### Menu de opções (DropdownMenu)

`DropdownMenu` (`components/ui/dropdown-menu/`, 2026-09-07) é o menu de opções colado no próprio gatilho, no padrão das camadas do menu lateral, feito para o chevron de cada item de lista (o primeiro uso é o cliente, sobre uma referência do usuário). Em 2026-09-10 ganhou quatro coisas, a pedido da janela da tarefa: **gatilho sem caixa** (`triggerContent`), em que o valor da ficha é o próprio botão (`inline-flex`, e não `display: contents`, que zera o retângulo do elemento e fazia a caixa nascer em 0,0); **mídia por item** (`media`), para o rosto da pessoa e a etiqueta de prioridade entrarem no lugar do glifo; **busca acima de cinco opções**, que limpa o que foi digitado ao fechar; e **teto de altura** de 340px no computador, com a busca parada no topo e só a lista rolando, porque uma lista de vinte pessoas virava uma tira do tamanho da tela.

- Gatilho é o `IconButton` fantasma com o chevron duplo (ou o ícone passado), com `aria-haspopup` e `aria-expanded`. No desktop abre uma caixa de vidro de 280px colada no gatilho: o `useAnchoredPosition` estima o lado pela contagem de itens antes de pintar e, no mesmo quadro, um `useLayoutEffect` mede a caixa já montada e a encaixa na janela de verdade, abaixo do gatilho se couber, acima se couber melhor, e presa às bordas com 16px de folga quando não cabe de jeito nenhum, com a rolagem interna da caixa cuidando do resto (ajuste de 2026-09-07: a estimativa sozinha cortava a caixa em cima quando ela virava para cima perto do pé da tela). A posição chega em pixels resolvidos, sem `translate` para o lado de cima, e o gênio de entrada e saída das camadas nasce do lado do gatilho; fecha por toque fora (`useOutsideDismiss`). No celular é a bandeja do `Dialog` em vidro e sem escurecimento, a mesma decisão da troca de time, com a lista rolando por conta própria dentro do painel, que esconde o que transborda (sem isso ela era cortada no fim). **Na bandeja as seções ganham ar e título forte** (2026-09-08): listadas como no desktop, separadas pelo fio, com mais respiro entre uma e outra e o título em `footnote` semibold na tinta cheia, recuado o mesmo que as linhas para nascer alinhado ao glifo delas, para dar para discriminar cada grupo numa lista que rola (um bloco com fundo por seção durou uma rodada e saiu a pedido); o item marcado ganha fundo, porque no dedo não há hover para acompanhar o check; o vidro da bandeja subiu de 40% para 72% de fundo em `--glass-sheet-bg`, porque sobre o painel o menu ficava difícil de ler.
- Seções (`DropdownSection`) separadas pelo fio da casa, com título opcional em `caption1` ("Acompanhamento"). Itens de ação (`DropdownAction`) viram botão, `Link` para rota da casa ou `<a>` em outra aba para endereço externo, na linha do menu (36px, 44 no toque, hover no preenchimento da casa), com ícone à esquerda e, no fim da linha, a contagem em `Badge` neutro ("12"), o selo do plano que libera no mesmo chip neutro e suave da Assinatura no menu da conta ("Pro"; o roxo sólido durou uma rodada) e a seta de mais opções quando há submenu; `tone="danger"` pinta a linha em vermelho ("Excluir"). Itens de interruptor (`DropdownToggle`) são um `label` com o `Switch` pequeno no fim, então clicar em qualquer ponto da linha alterna; a linha é `menuitemcheckbox`.
- Escolher uma ação fecha o menu; alternar um interruptor não. **Linha de rota não fecha ao clicar**: ela mostra o giro no fim enquanto o `useLinkStatus` diz que a navegação anda, e o menu fecha quando ela termina ou quando o caminho muda (ajuste de estado durante o render sobre o `usePathname`), porque fechar antes deixava a pessoa sem saber se o clique pegou (2026-09-08). Ação com `keepOpen` também não fecha: é para menu de filtro, em que a pessoa ajusta várias coisas antes de sair (2026-09-08). O gatilho é fantasma por padrão e aceita `trigger`, um `Pick` de variante, canto e cores do `Button`, que é como a barra de busca veste os dela. Ao abrir, o foco vai para o primeiro item; setas, Home e End andam pelos itens, Escape fecha e devolve o foco ao gatilho. Os itens ficam fora do Tab (`tabindex="-1"`) para a navegação ser só por setas.
- O submenu é só a seta por enquanto: a opção age como ação simples. Quando existir, abre outra camada ao lado.
- `ClientMenu` (`features/clients/components/client-menu.tsx`) monta as opções de um cliente no padrão pedido: Visualizar (`/clientes`), Editar, Gerar orçamento (`/orcamentos/novo?cliente=<id>`), Gerar cobrança (`/cobrancas`) e Gerar contrato (`/contratos`), os três documentos com seta e selo Pro, e Chamar no WhatsApp (`wa.me` com o telefone, só quando há telefone); seção Acompanhamento com Histórico (contagem) e Mapa de relação; interruptores Ativo e Favoritar; e Excluir em vermelho. O sino no rodapé do menu abre a caixa colada nele, que sobe porque ali não há espaço embaixo: cabeçalho com o que falta ler, categorias em aba e a lista. Bandeja no celular, onde o rodapé do menu fica longe do polegar.

- Quatro abas: todas, ação necessária, revisões e sistema. A fila rola na horizontal e desbota nas pontas, como a fila de atalhos da busca, porque quatro categorias não cabem numa tela estreita.
- A aba em vigor é marcada por traço embaixo, e não por preenchimento: preenchimento ali competiria com a marca de não lido de cada linha.
- Não lido acende um ponto na frente do título, e a linha lida cai de opacidade. Pintar a linha inteira transformava a lista num bloco de cor com meia dúzia de itens. Clicar na linha marca como lida.
- O sino carrega o contador do que falta ler na própria quina, virando "9+" acima de nove, e o cabeçalho tem só silenciar e fechar. Silenciar é preferência de interface, então mora em cookie e sobrevive ao recarregar; o sino troca para o riscado enquanto está mudo.
- **Três modos empilhados** (2026-09-09): busca e sino, a paginação da lista à vista e salvar e sair de uma janela, montados um sobre o outro e trocados pelo fundido do `barMode`, na ordem de prioridade janela → lista → busca. A largura é a do modo em vigor, e não a do maior deles (acerto de 2026-09-10, acima). ## Ecossistema web + mobile (mesmo banco)

Haverá app Android/iOS usando literalmente o mesmo Supabase. Consequências que valem desde já:

1. **Regra de negócio no banco primeiro**: RLS, constraints, funções SQL (RPC) e triggers. Web e mobile falam com o mesmo Postgres e recebem as mesmas garantias.
2. **`service.ts` por feature**: lógica que precisa de segredo de servidor (Stripe, Resend, OpenAI, Redis) fica em `src/features/<dominio>/service.ts`. Server Actions (web) e Route Handlers em `src/app/api/v1/*` (mobile) são adaptadores finos sobre o mesmo service. Nunca duplicar lógica entre os dois.
3. **API para o app**: `src/app/api/v1/*` autentica por `Authorization: Bearer <access_token>` do Supabase usando `createClientFromRequest` em `src/lib/supabase/api.ts`. A RLS continua valendo porque o cliente carrega o JWT do usuário.
4. **Auth compartilhada**: Supabase Auth no mobile (deep link `specular://auth/callback` entra em `additional_redirect_urls` quando o app existir). MFA TOTP usa as mesmas APIs. Apple Sign In passa a ser obrigatório quando houver login social no iOS, então a conta Apple Developer entra junto com o app.
5. **Tipos e validação compartilháveis**: `src/types/database.ts` (gerado) e `src/features/*/schemas.ts` (zod) são o contrato. Se o app for Expo/React Native em TypeScript, esses arquivos migram para um pacote compartilhado em monorepo sem reescrever.
6. **Multi-tenant desde o schema**: organizações e membros modelados no banco antes de qualquer feature, porque o app precisará do mesmo contexto de conta.

O primeiro domínio montado nesse formato é `organizations`: `service.ts` recebe o cliente Supabase de fora e não sabe quem chamou, `actions.ts` é a casca com sessão, zod, rate limit e revalidação, e `api/v1/organizacoes` (mais `organizacoes/membros`) é a mesma casca para o aplicativo, com `authorizeRequest` de `lib/api/v1.ts` cuidando de token, teto de requisições e leitura do corpo com limite.

## Cobrança e permissão por plano

Montado em 2026-09-01. Três fontes de verdade separadas, de propósito: **o Stripe guarda o dinheiro**, **o banco guarda quem pode o quê** e **`features/billing/plans.ts` guarda o texto de vitrine**. Nenhuma das três repete a outra, então não existe divergência para reconciliar.

### O que vive no banco

| Tabela | Papel |
| --- | --- |
| `billing_plans` | catálogo: código, nome, degrau (`tier`), dias de teste, se o teste exige cartão, se é pago |
| `billing_prices` | mapa plano + ciclo para o `stripe_price_id`. Sem valor: o valor está no Stripe |
| `plan_features` | catálogo de recursos que o plano libera (`flag` liga e desliga, `limit` guarda teto) |
| `plan_entitlements` | a permissão em si: um recurso por plano, com `enabled` e `limit_value` |
| `organization_subscriptions` | uma linha por organização: plano, ciclo, status, ids do Stripe, período, cartão |
| `billing_trials` | teste gratuito consumido, chaveado por organização e plano |
| `billing_events` | id do evento do Stripe já processado, para reentrega não processar de novo |

**`plan_features` e `plan_entitlements` nascem vazias.** Cada condição de plano entra junto com a tela que a exige, nunca antes. Sem linha, `plan_allows` nega e `plan_limit` devolve zero: negado por padrão.

### Como se define a regra de uma tela

Duas linhas de SQL numa migração de `billing`, e mais nada:

```sql
insert into public.plan_features (key, kind, name)
values ('active_projects', 'limit', 'Projetos ativos');

insert into public.plan_entitlements (plan, feature_key, enabled, limit_value)
values ('free', 'active_projects', true, 3),
       ('pro', 'active_projects', true, null),        -- nulo com enabled = ilimitado
       ('alliance', 'active_projects', true, null);
```

A partir daí a regra vale em qualquer lugar, sem código novo:

- Em policy de RLS: `using (public.plan_within_limit(organization_id, 'active_projects', (select count(*) from public.projects p where p.organization_id = ...)))`.
- Em `service.ts`: `client.rpc("plan_allows", { p_organization_id, p_feature_key })`.
- Na interface: o `Button` já tem `locked` com `plan`, que anexa a etiqueta do plano sem tirar o clique, para o clique levar ao upgrade.

Recurso que não existe em `plan_features` **derruba a chamada com erro**, em vez de negar ou liberar em silêncio: chave escrita errada aparece no primeiro teste.

### Funções de permissão

`organization_plan(org)` é a única que decide plano em vigor, e é o lugar único onde os status com direito estão escritos (`trialing`, `active`, `past_due`). Cancelado, expirado e não pago caem no gratuito sem ninguém mais precisar saber disso. As outras se apoiam nela: `current_plan()`, `plan_at_least(org, plano)`, `plan_allows(org, chave)`, `plan_limit(org, chave)`, `plan_within_limit(org, chave, quantidade)`, `trial_available(org, plano)`, `can_manage_billing(org)`.

### Quem escreve

Nenhuma tabela de cobrança tem policy de escrita. Ninguém troca o próprio plano falando direto com a API, nem o dono do time. As duas portas são:

- `attach_billing_customer(org, cliente)`, aberta para `authenticated`, exige owner ou admin e nunca sobrescreve um cliente já vinculado.
- `sync_subscription(...)`, **revogada de `authenticated`** e concedida só a `service_role`. Só o servidor escreve plano e status, e sempre com o que o Stripe devolveu, nunca com o que o pedido mandou.

### Fluxo de pagamento

O formulário é nosso, o cartão é do Stripe. Saiu o Payment Element (que traz rótulo, caixa, abas e o Link do provedor prontos) e entraram os três elementos avulsos, `CardNumberElement`, `CardExpiryElement` e `CardCvcElement`, cada um dentro de um `FieldShell` com `Label` nosso e mensagem de erro nossa. O que continua sendo do Stripe é só o campo em si, um iframe por campo, e é isso que mantém número, validade e CVV fora do nosso DOM e dos nossos servidores (PCI SAQ A). Campo de cartão de verdade no nosso HTML exigiria certificação PCI DSS nível 1 e liberação do Stripe, então não é caminho.

Dentro do iframe a nossa folha não chega: o que atravessa é o objeto `style` de `use-card-style.ts`, com as cores resolvidas em RGB por uma sonda invisível, porque `light-dark()` não sai pronto de `getPropertyValue` (mesma técnica do `GradientBlinds`). Trocar de tema reconstrói o estilo e o `react-stripe-js` repassa por `element.update`. A fonte entra por `fonts: [{ cssSrc }]` apontando para o Inter do Google Fonts: o arquivo do `next/font` é servido do nosso domínio sem CORS, e o iframe, que é outra origem, não consegue buscar. Falhando, cai no tipo do sistema. O raio e a superelipse ficam com o `FieldShell`, que é nosso, então a caixa do cartão tem o mesmo contorno de qualquer outro campo.

Confirmar é `confirmCardSetup` ou `confirmCardPayment` com o `clientSecret` e o elemento do número; o Stripe junta validade e código sozinho, porque os três vieram do mesmo `Elements`. A autenticação do banco abre num modal do próprio Stripe e a pessoa não sai da tela.

Elemento de cartão avulso monta **sem segredo nenhum**, e é por isso que a prévia e a vitrine mostram o formulário de verdade em vez de um espaço reservado: o `clientSecret` só é usado na confirmação, que a prop `preview` desliga.

Dois caminhos, escolhidos no servidor:

1. **Com teste gratuito** (Pro, 7 dias): cria um SetupIntent, guarda o cartão, e só então cria a assinatura com `trial_period_days`. Criar a assinatura antes daria sete dias de plano pago a quem abandonasse o formulário no meio.
2. **Sem teste gratuito**: cria a assinatura com `payment_behavior: "default_incomplete"` e devolve o segredo de `latest_invoice.confirmation_secret`. O plano só passa a valer quando o pagamento confirma, porque `incomplete` não está na lista de status com direito.

`trial_settings.end_behavior.missing_payment_method: "cancel"` fecha o caso do teste que termina sem cartão. O teste é uma vez por organização e por plano, garantido por `billing_trials`: cancelar e assinar de novo não devolve período grátis.

### Webhook

`api/webhooks/stripe` confere a assinatura com `constructEventAsync` antes de ler qualquer coisa, e então **relê a assinatura no Stripe** em vez de confiar no corpo do evento, porque reentrega fora de ordem gravaria estado antigo por último. `setup_intent.succeeded` é a rede de segurança do fluxo de teste: se a aba morrer depois de confirmar o cartão e antes da action responder, o webhook ativa o plano do mesmo jeito, e passar duas vezes não duplica porque a criação reaproveita a assinatura existente. O id do evento entra em `billing_events` **depois** de processar, senão uma falha de escrita perderia o evento; falha responde 500 para o Stripe reentregar.

### Comandos

| Comando | O que faz |
| --- | --- |
| `npm run stripe:sync` | publica produto e preço de cada plano pago no Stripe e grava o `stripe_price_id` em `billing_prices`. Idempotente: produto tem id fixo (`specular_<plano>`) e preço é achado por `lookup_key`. Preço com valor diferente do catálogo vira preço novo com a mesma chave, e o antigo é desativado dos dois lados, para assinatura em vigor continuar no que foi assinado |
| `npm run billing:probe` | teste ponta a ponta contra o Stripe em modo teste e o banco hospedado, pela mesma porta que o aplicativo usa (`api/v1` com Bearer). Cria usuário e time, assina, confirma cartão de teste, confere banco, cancela, retoma, dispara webhook assinado e apaga tudo no fim |

O `stripe:sync` lê `plans.ts` com `--experimental-strip-types`, para o catálogo continuar tendo uma fonte só.

## Telas

### Painel

O painel abre com a pessoa, e não com o nome da tela: avatar, nome e uma frase curta de boas-vindas à esquerda, e a fila de ações à direita. Primeira tela montada um bloco por vez, a partir de 2026-09-04; por enquanto só o cabeçalho existe.

- `PageHeader` (`components/layout/page-header/`) é o cabeçalho genérico de página: `leading`, título, linha de apoio e `actions`, Server Component com CSS Module. Título e linha de apoio ficam a 2px um do outro, porque são uma identidade só. O vão entre as ações é o do menu, 4px, em qualquer largura: com 8 os ícones liam como soltos. Em tela estreita as ações descem para a linha de baixo em vez de sumir, salvo em `compact`: aí no celular ficam a foto e o título na tela numa linha só, a linha de apoio vai para o leitor de tela, e as ações ficam na mesma linha na versão pequena dos botões (36px, com `--touch-target` rebaixado, a pedido) a 4px uma da outra; o cabeçalho não quebra (`nowrap`), porque a identidade cede (`flex: 1 1 0`) e o título encurta por reticências antes de as ações descerem (ajustes de 2026-09-07; antes o título saía da tela, e depois o nome quebrava o cabeçalho em duas linhas no iPhone). O painel usa `compact`, e o botão de criar orçamento vira só ícone no celular por CSS (os dois existem na marcação, cada largura mostra um), para não saltar na hidratação.
- A frase de boas-vindas sai de `features/dashboard/greetings.ts`, sorteada por pessoa e por dia, e não por carga: o período do painel vive na URL e cada troca refaz a página no servidor, então uma frase nova a cada carga trocaria a cada clique e leria como defeito.
- Ações só em ícone, nesta ordem: buscar (abre a mesma busca do menu), período e a engrenagem de personalizar o painel, que abre a gaveta de ordem e visibilidade dos blocos. Criar orçamento é a ação principal, a única com texto, e leva a `/orcamentos/novo`.
- O período é o `DropdownMenu` da casa com o ícone de calendário no gatilho e o escolhido marcado (`selected`, item `menuitemradio` com o check no fim), a mesma camada do chevron duplo dos clientes, com a posição medida antes de pintar para abrir onde cabe (2026-09-07; até então era o `Listbox` em `iconOnly`, que segue existindo para outros usos). O valor em vigor vai no nome acessível do gatilho. A escolha vai para `?periodo=` por `router.replace`, validada com zod no servidor (`features/dashboard/period.ts`; valor inválido cai em "Este mês"), porque é ela que os blocos do painel vão ler. Na vitrine o `demo` guarda a escolha só na tela.
- `DashboardScreen` (`features/dashboard/components/`) é a tela inteira, cabeçalho e grade, montada pela página com dados do banco e pela prévia `/previa/painel` com os dados de exemplo do menu, dentro da `AppFrame`, que é a moldura do `AppShell` sem o banco. O cabeçalho fica grudado no topo enquanto a página rola (2026-09-07): `sticky` na coluna de conteúdo da concha, que é quem rola, desbotando para o transparente como o cabeçalho do site, e não como faixa sólida (pedido do mesmo dia): o fundo é um degradê da cor da página até o nada e o borrão das camadas (`--glass-layer-blur`) é desbotado por uma máscara que vai de cima a baixo (cheia até 20%, nada em 100%), então cor e borrão somem juntos e o que rola por baixo vai ficando nítido conforme desce; com a máscara só no pé, o borrão cheio fazia o degradê ler como faixa sólida, o que o usuário apontou. Sangra o recuo da tela pelos três lados e o devolve por dentro, com uma faixa extra de 24px embaixo onde o degradê acaba. Degradê, borrão e máscara vivem num pseudo-elemento atrás do conteúdo (`isolation: isolate` no invólucro), e não no invólucro: a lista do período nasce dentro do cabeçalho e desce por baixo dele, e uma máscara no invólucro a apagaria. Parado no topo nada aparece. Fica só acima dos blocos (`z-index: 1`), abaixo de qualquer camada flutuante. A tela traz o próprio recuo, 16 no celular e 24 daí para cima, sem teto de largura: o painel aproveita a tela inteira. A concha continua sem recuo.

Todo bloco tem duas linhas de altura, menos os dois pares que dividem uma coluna: conquistas com projetos, e equipe com desafio diário (o desafio entrou em 2026-09-07, quando equipe passou de duas linhas para uma, a pedido). Uma coluna até 48rem; duas até 72rem, em três pares de blocos altos; três colunas a partir de 72rem (896px de conteúdo ao lado do menu, a largura da referência), no mapa pedido: conquistas em cima de projetos na primeira coluna (conquistas subiu para a primeira posição em 2026-09-07, a pedido, para a gamificação abrir o painel), financeiro e clientes ao lado, e embaixo tarefas e último orçamento, altos, com equipe e desafio diário entre os dois. A linha é fixa em 12,5rem em toda largura (bloco com lista rola por dentro, e não estica a página; no celular e no tablet crescia com o conteúdo até 2026-09-07), e no desktop as quatro linhas dividem o que sobra abaixo do cabeçalho entre o piso de 12,5rem e o teto de 60rem da grade, então bloco nenhum estica a linha e gera rolagem; só em tela mais baixa que o piso a página rola. Vão de 16 entre blocos e 24 entre cabeçalho e grade. Cada bloco leva o ícone da rota correspondente no menu e um atalho tipado por rota para a tela dela. Esse mapa é a estrutura, e não muda: quando a pessoa esconde ou reordena blocos pelo ajuste do painel, a grade entra em `data-custom` e a posição passa a ser calculada por `packDashboard` (`features/dashboard/layout.ts`) na mesma estrutura, andares de duas linhas com um alto inteiro ou dois baixos empilhados por coluna, na ordem escolhida, uma vez por largura (na coluna única do celular a ordem é literal; com mais colunas um alto nunca parte um par de baixos: caindo entre dois, o par fecha primeiro e o alto entra logo depois, a regra do usuário), e o bloco chega com coluna e linha em variáveis (`--c1`/`--r1`, `--c2`/`--r2`, `--c3`/`--r3`) e a altura em `--span`; alto continua alto e baixo continua baixo. ### Topo e barra de página

O topo padrão de toda página da aplicação, menos o painel, que abre com a pessoa e não se enquadra (2026-09-08, sobre uma referência do usuário).

- **`Topbar`** (`components/layout/topbar/`) tem três partes: a rota até a página à esquerda, o nome dela no meio, como `h1` em `headline` semibold, e o uso da IA na ponta direita. A rota é minimalista, só os nomes separados por barra, na tinta secundária (2026-09-08, a pedido): a área do menu e, quando a página mora numa pasta, o nome dela. Sem glifo, sem azulejo colorido e sem link, porque quem leva a outro lugar é o menu lateral; por isso `NavCrumb` carrega só o `label`. A rota não repete o nome da página, que já está no meio da barra. No celular a rota sai e o nome volta para a esquerda, porque numa tela estreita ela comeria o título. Rota e nome saem de `navLocation` (`components/layout/nav.ts`), que acha a rota no menu, a fonte única das rotas; a página troca o nome por `title` quando se chama diferente do menu. A base de clientes deixou de trocar em 2026-09-08: no topo ela se chama "Base de clientes", igual ao menu. `navLocation` e `isCurrent` seguem em `nav.ts`, servindo à busca e ao menu.
- **O caminho e o nome saem de `navLocation`** (`components/layout/nav.ts`), que acha no menu onde a rota está. Vem de lá, e não de um mapa novo, porque `navGroups` já é a fonte única das rotas: página que nasce no menu ganha o topo de graça e não há um segundo mapa para sair de sincronia. Entre duas rotas que casam ganha a mais específica, senão `/orcamentos/novo` leria como "Acompanhar", que também casa por prefixo. - **O caminho é uma trilha, e não um menu** (a pedido, sobre uma referência de breadcrumb): os degraus separados por barra, cada um com o glifo do menu na frente, em `footnote` medium. **O degrau da pasta leva o glifo num azulejo cheio no matiz dela**, com o traço em branco, e o da área sai solto e apagado: é o contraste da referência entre o contexto largo e o lugar onde a página mora de verdade. O matiz é o mesmo que a busca já usa para tingir as páginas daquela pasta, então a cor de cada seção é a mesma nos dois lugares. O último degrau é o mais escuro, porque é o mais perto da página. Não é link nem dropdown: ele diz onde a pessoa está, e quem leva a outro lugar é o menu lateral. Marcação de `nav` com `ol`, porque é isso que uma trilha é e o leitor de tela anuncia a ordem dos degraus. Para isso o grupo do menu ganhou `icon` em `nav.ts`, que antes só as pastas tinham.

- **O topo fica grudado no topo enquanto a página rola** (a pedido, 2026-09-08): `sticky` na coluna de conteúdo da concha, que é quem rola, com fundo sólido na cor da página e `z-index: 1`, só acima do conteúdo; as camadas flutuantes, que vão por portal, ficam acima dele. Abaixo de 48rem a tela vai a `height: auto` com `min-height: 100%` e trilhas automáticas, então o pai que rola volta a ser a coluna da concha e o topo fica preso o tempo todo.

### Clientes

Antes o check só aparecia com a resposta do servidor, e a lista parecia lenta. Situação e contato entraram na URL em 2026-09-08 (`situacao`, `email=1`, `telefone=1`), lidos por zod como os outros; os valores "outros" e "ativos" seguem válidos na URL mesmo sem opção própria no menu. No celular elas saem, porque a linha já toma a largura toda. Uma rodada com visão em tabela ao lado da grade, escolhida num seletor da barra e guardada em cookie, nasceu e saiu no mesmo dia, a pedido: a grade é a única visão da base. Excluir e exportar sobre a seleção saíram da barra no mesmo dia, a pedido; a marcação dos cartões fica, para as ações que virão.

Trocar qualquer filtro leva de volta para a primeira página, senão a pessoa cairia numa página que o novo filtro não tem. O campo de busca espera 320ms a pessoa parar de digitar, senão seria uma ida ao servidor por letra. ### Catálogo

Produtos e serviços que a equipe vende, na mesma estrutura da base de clientes: barra, grade de cartões ou tabela, paginação e a ficha na gaveta lateral. O filtro vive na URL e o servidor faz o trabalho (`listCatalog` em `features/catalog/list.ts`); a lista vem de `list-preview.ts` até o domínio nascer no banco.

- **Produto e serviço são a mesma ficha com fatos diferentes.** Serviço tem prazo e revisões; produto tem estoque (`CatalogStock`: quantidade e mínimo de aviso). Produto sem estoque é sob demanda, como hospedagem, e a ficha diz isso em vez de esconder a seção.
- **O estoque se lê num lugar só**: `readStock` em `list-options.ts` devolve frase, versão curta ("48/100", quantidade sobre capacidade, pedido de 2026-09-08), cor e quantidade. Esgotado em vermelho, no mínimo ou abaixo em laranja, o resto em verde; sob demanda em neutro com "∞/∞" na versão curta; serviço devolve nulo e a tabela mostra "∞/∞" também. Cartão, ficha e tabela usam a mesma leitura, então nunca discordam. O modelo (`CatalogStock`) tem quantidade, capacidade e mínimo de aviso.
- **O cartão** traz a arte, situação, preço e leque em cima; nome e descrição em duas linhas; a fila de etiquetas (categoria, prazo ou estoque, cobrança, tipo); e uma linha de venda apagada no pé, com quantos orçamentos e quantos fecharam. Fora de linha, o que é do item apaga e a situação e o leque ficam inteiros.
- **A ficha** abre na gaveta com o fundo da página, na moldura da ficha do cliente: cabeçalho preso com nome, referência, leque e fechar; identidade com a arte, o nome com as etiquetas de situação e tipo e a categoria (o botão **Gerar orçamento** que ficava na ponta saiu a pedido de 2026-09-08; a ação vive no leque). O centro é **Preço e condições em grade 2×** (decisão de 2026-09-08): oito fatos em quatro linhas, rótulo curto em cima e valor curto embaixo, cada um numa linha só. Preço, cobrança, custo, margem, desconto, garantia e, para produto, estoque (com a cor do estado) e aviso; para serviço, prazo e revisões. A grade força as duas colunas no desktop alcançando o primitivo de fatos por elemento, porque ele empilha numa coluna com rótulo à esquerda e oito fatos assim viravam lista comprida. Depois vêm sobre, orçamentos recentes (com total e aprovação na cabeça), etiquetas e anotações. Sem azulejos, sem listas de escopo e sem seção de registro, a pedido.
- **A tabela** é o `DataTable` em densidade compacta, com marcação por linha, zebra, altura fixa da tela (`fill`, com linhas vazias completando o que sobra), ordem só em preço, orçamentos e desde (a pedido de 2026-09-08; nome, criado por e estoque não ordenam, e não há ordem padrão) e colunas: criado por, item, tipo (etiqueta em teal para produto e índigo para serviço, por `kindTones`, a mesma cor no cartão e na ficha), preço com a cobrança na mesma linha, estoque ("48/100" com a cor do estado, "∞/∞" para serviço e sob demanda), prazo em etiqueta ("Indeterminado" quando não há), situação, orçamentos, desde quando. Criado por é a primeira coluna (a pedido de 2026-09-08, antes do item), a bolinha pequena e o nome de quem cadastrou (`createdBy` no modelo, que a ficha repete na linha da referência). Orçamentos são as bolinhas de até quatro clientes que já receberam o item (`Avatar` xs em `AvatarGroup`, um rosto por cliente dos orçamentos recentes da ficha, entrando 4px um sobre o outro) e o total da base ao lado, em footnote medium, e "Não condiz" quando não há nenhum; a versão com a contagem e o percentual de aprovação durou uma rodada.

- **A folha é uma pilha em coluna** (acerto de 2026-09-09), e não uma grade: com altura fixa a grade esticava as linhas e abria vãos enormes entre as seções; em coluna tudo assenta no topo e só a assinatura desce, pela margem automática, o que dá o mesmo desenho na prévia de folha fixa e na página pública de altura livre.
- **A assinatura é o registro digital** (`QuoteSignature`, 2026-09-10, a pedido), no lugar da linha em branco que existia para assinar à mão: o rosto de quem vendeu em círculo (o `Avatar` da casa, com o desenho gerado quando não há foto) com "Documento assinado digitalmente", o nome em caixa alta, a data e por onde o documento saiu, e **a linha de assinar embaixo deles**, que é onde ela fica num documento: assina-se sobre a linha. Os detalhes abrem a **janela da casa**, que no celular é a bandeja de baixo, com a ficha em duas colunas no desenho do `DetailsDialog`, no lugar do cartão flutuante que abria no toque; ela é camada da interface, e não parte do documento, então segue o tema do aparelho, ao contrário da folha, que é papel branco sempre. Falar com a equipe desceu para o pé dessa ficha, porque é o assunto dela. Voltar é o histórico do navegador e só entra quando há para onde voltar (`history.length`, lido por `useSyncExternalStore`, que dá "não há" no servidor e no link aberto em aba nova). A fila também perdeu a medida reduzida que tinha no celular, de 2rem, abaixo do alvo de toque mínimo: com cinco ações o espaço dá para o tamanho da casa.
- **Baixar o PDF tem dois caminhos, e o do celular é a folha de compartilhar do sistema** (2026-09-10, em duas rodadas do mesmo relato: no Safari do iPhone não dava para baixar). O primeiro acerto tirou o `blob:` montado na tela, que tinha três problemas somados — o link nunca entrava no documento, e o Safari ignora clique em elemento fora dele; o endereço temporário era liberado no ciclo seguinte, antes de o Safari acabar de ler o blob; e o iOS **não respeita `download` em `blob:`**. Só que a âncora com `download` também não resolve no iPhone, onde o atributo simplesmente não existe: o PDF abria no visualizador e ficava sem saída dali. Então **no celular o arquivo é buscado e entregue ao `navigator.share`**, e o iPhone abre a folha que ele já conhece, com Salvar em Arquivos, WhatsApp e imprimir na mesma lista, que é o que se quer fazer com um orçamento; **no desktop segue a âncora com `download`**, que o navegador resolve direto e nomeia pelo `Content-Disposition: attachment` da rota. A capacidade é medida **antes** de buscar o arquivo, com um `File` vazio do mesmo tipo, porque compartilhar precisa do gesto da pessoa ainda valendo e cada espera no caminho gasta essa permissão; quem não compartilha arquivo desvia para o download sem baixar nada à toa. Fechar a folha é `AbortError` e não avisa nada; um `NotAllowedError`, do gesto que expirou, cai no download em vez de mostrar um erro que ninguém pode consertar. **O que vai ao `share` é só o arquivo, e com nome de anexo** (acerto de 2026-09-10, do relato de que o WhatsApp do iPhone recusava o envio com "Não foi possível enviar a mensagem", enquanto Salvar em Arquivos funcionava): a folha do iOS monta a prévia a partir do arquivo, e sem prévia o destino recebe um anexo degradado — quem só precisa dos bytes salva, quem precisa do anexo íntegro falha. As duas causas eram nossas: o `title` ao lado dos `files`, que dá dois assuntos à folha, e o nome com acento e vírgula. Agora o `share` leva `{ files }` e nada mais, e o nome do anexo passa por `quoteAttachmentName` (sem acento, sem vírgula, espaço em sublinhado). O nome bonito continua onde é lido como texto: o `Content-Disposition` da rota e o `download` da âncora no desktop. O `Button` da casa ganhou a prop `download`: com ela o clique é transferência, e não navegação, então nem o `next/link` por baixo intercepta nem o giro de link pendente entra.
- **Compartilhar**: `share.ts` monta o endereço público absoluto e o link `wa.me` no número do cliente. **A mensagem é escrita na formatação do WhatsApp** (2026-09-09, a pedido): negrito entre asteriscos, itálico entre sublinhados, linhas curtas e um bloco por assunto separado por linha vazia, na ordem em que se lê no celular (quem fala e por quê, o título com o número, total com parcelas e a oferta de à vista, validade em itálico) e o link sozinho na última linha, que é o que faz o WhatsApp desdobrar a prévia com a imagem do documento. Sem emoji, no tom da casa.
- A base de exemplo é `list-preview.ts`: 42 orçamentos com os clientes e os itens das outras prévias, tokens determinísticos, situações em ciclo e datas relativas a hoje. A equipe em vigor entra como emissora na tela do app (`queries.ts`, `loadQuotesScreenData`: nome e logo do banco, contatos da prévia); a página pública usa a emissora da prévia, porque não tem sessão.
- Pendências: gravar de verdade (criar, editar, enviar, resposta do cliente com a data e a visualização) por `service.ts` com Server Action e `api/v1`; marcar situação à mão, duplicar, excluir e histórico; e-mail com o link; contatos da equipe no cadastro do time.

### Tarefas

**Tarefas é uma pasta no menu**, e não uma página solta (2026-09-10, a pedido, em duas rodadas do mesmo dia: entrou como página solta com o `ListChecksIcon` do bloco do painel e virou pasta na rodada seguinte). Escolher Tarefas abre, dentro do menu, a **arquitetura de pastas e projetos** com "Todas as tarefas" no topo, e é ali que a pessoa diz para onde vai. As páginas são duas: `/tarefas`, o quadro de tudo, e `/tarefas/<slug>`, o quadro de um projeto. As duas são a mesma tela (`TasksScreen`), com o topo padrão da aplicação e a `PageToolbar` de sempre, e **vão ter duas visões**: o quadro em kanban, que é o foco, e a lista, combinada para depois. Enquanto a lista não existe, a barra não mostra o seletor de visão: ele é opcional na `PageToolbar` de propósito, e um grupo de escolha com uma opção só não escolhe nada.

- **A arquitetura** (`features/tasks/tree.ts`) é pasta dentro de pasta e, nas folhas, projeto. A pasta só organiza e **não é destino**: não tem endereço, e clicar nela abre e fecha o galho. Quem tem quadro é o projeto, com endereço próprio e as etapas dele. O projeto guarda o identificador do projeto (`PRJ-2026-0007`), o mesmo que a tarefa carrega, que é como as duas pontas se encontram; **identificador nulo é o balde "Sem projeto"**, para tarefa solta continuar tendo lugar na arquitetura em vez de existir só na lista de todas. `buildTaskTree` resolve a árvore com a contagem **do que está em aberto** em cada nó, somando os filhos nas pastas: no menu a contagem responde "quanto falta aqui", e zero não desenha etiqueta, porque um zero em cada linha é ruído.
- **A árvore no menu** (`TasksTree`, sobre duas referências do usuário) veste a pele das linhas do menu e acrescenta três coisas. O **degrau** por nível, que acumula pelo aninhamento em vez de alguém contar a profundidade. O **cotovelo** que liga o filho ao pai: uma caixa sem fundo com a borda esquerda descendo até a meia altura da linha e a de baixo virando para a direita, com o canto arredondado ligando as duas, mais o fio que segue para o irmão de baixo em quem não é o último (o `├` e o `└` da referência), tudo desenhado no invólucro do galho para não atravessar o realce do hover, e em **1px cheio** em vez do `--menu-line` de 0,6px da casa, porque 0,6px em tela de duas vezes caía em pixel diferente da borda do cotovelo e o galho saía picado. E o **azulejo de cada projeto**, com glifo e matiz próprios, que é o que distingue um quadro do outro de relance, com a contagem no mesmo matiz; a pasta segue com o glifo solto e a contagem neutra, porque ela é o caminho e soma projetos de matizes diferentes. O glifo atravessa a fronteira do servidor **por chave**, e não como componente, porque a árvore é montada na concha e o menu é componente de cliente. **O caminho até o projeto aberto sai em fio mais forte** (`data-route`), que é a rota completa de onde a pessoa está; o resto fica no fio de estrutura, senão nada ficaria em evidência. Quem abre se mostra no próprio glifo, aberto ou fechado, e no `aria-expanded`: seta de abrir separada saiu porque roubava o lugar em que o cotovelo encosta. O galho do caminho nasce aberto e daí em diante quem manda é o clique, em estado de sessão e não em cookie, senão o menu abriria num galho e o servidor mandaria outro. Criar mora no cabeçalho do galho, no `+` ao lado do voltar, com "Novo projeto" e "Nova pasta" declarados e ainda sem regra.
- **O gancho no menu** é `tree?: "tarefas"` no `NavFolder`: pasta e projeto vêm do banco e têm endereço próprio, então não caberiam em `items`, que é a lista fixa de rotas. A árvore chega ao `Sidebar` por prop, resolvida no `AppShell`, como as notificações e o aviso. O `Sidebar` aceita também `taskRoute`, que só a prévia de front usa, porque ela mora em outro endereço e o menu não teria como saber qual projeto está aberto (mesma razão do `demo` da tela do painel).
- **As etapas são as colunas, e cada projeto tem as suas** (`features/tasks/stages.ts`, 2026-09-10). O catálogo tem oito, cada uma com nome, glifo, matiz e o `kind` que diz em que ponto do caminho ela está: Backlog (bandeja, cinza), A fazer (círculo tracejado, azul), Em andamento (círculo meio cheio, laranja), Bloqueada (proibido, vermelho), Em revisão (olho, roxo), Aprovação (polegar, índigo), Publicação (foguete, verde-água) e Concluída (check, verde). O **projeto escolhe quais usa e em que ordem**, então o quadro do site institucional tem Publicação, o da Padaria Aurora troca a revisão pelo Aprovação de quem decide e o do Estúdio Bravo tem Bloqueada. O catálogo é global e o projeto só seleciona, em vez de cada projeto inventar etapas com nomes soltos: é o que mantém `Task.stage` sendo um id que vale em qualquer lugar, porque com etapa por projeto o bloco do painel e a ficha teriam de conhecer o projeto para saber se a tarefa fechou, e o zod da URL não teria lista fechada para validar. Nome livre por equipe é para quando isso virar tabela.
- **A situação sai da etapa, e não é campo do modelo** (mesma data): as colunas são mais finas que os três estados que o painel e a ficha mostram, então `stageStatus` (em `labels.ts`) lê a situação do `kind` que a própria etapa do catálogo declara, e não de um segundo mapa, senão acrescentar uma etapa deixaria um dos dois sem ela. Guardar situação e etapa lado a lado faria a etiqueta dizer uma coisa e a coluna outra assim que alguém movesse o cartão. `Task` passou a ter `stage` no lugar de `status`, e o bloco do painel e a `TaskSheet` leem por `statusOf(task)`.
- **O quadro de todas as tarefas mostra as etapas em uso**, e não uma lista fixa (`stagesInUse`): ele cruza projetos com fluxos diferentes, e uma lista fixa esconderia o que está numa etapa que só um dos projetos usa. A conta é sobre a base inteira, e não sobre o que o filtro deixou, senão as colunas apareceriam e desapareceriam a cada busca. O quadro de um projeto mostra **todas as etapas dele**, mesmo vazias, porque coluna é lugar.
- **O cabeçalho da coluna** (`TaskColumn`, sobre uma referência do usuário) é o que a rodada de 2026-09-10 acertou: à esquerda a etiqueta da etapa numa pílula só, com o glifo no matiz, o nome na tinta cheia e a **contagem de tarefas dentro dela**; à direita o chevron duplo da casa, que abre o menu da etapa, e o "+" que cria uma tarefa ali. A pílula é montada no módulo da coluna, e não com o `Badge`: as contas de cor são as dele (70% do matiz sobre a tinta do texto, véu de 9% no claro e 12% no escuro), mas o primitivo não tem lugar para um chip no fim, e como `children` a contagem cairia dentro do texto que corta por reticências. A geometria é a de um chip dentro de uma caixa: 4px em volta da contagem nos três lados que ela encosta, então cima, baixo e direita são o mesmo recuo e ela fica grudada na direita com folga igual em volta; só o lado do glifo abre 12px, porque ali o que encosta é texto. O canto é `md` (12px num bloco de 32, abaixo da metade da altura) com a contagem em `sm` pela conta concêntrica, e não pílula: pílula em tudo saiu a pedido no mesmo dia. O nome e o glifo ficam um degrau acima na escala (`subheadline` e 18px), também a pedido, porque em `footnote` o título da coluna cedia destaque para o cartão.
- **A coluna não tem caixa** (a pedido, 2026-09-10): é o cabeçalho e a pilha, soltos na página, com o vão do trilho separando uma etapa da outra. Uma bandeja cinza atrás durou uma rodada e saiu, porque empilhava caixa dentro de caixa com o cartão. Etapa sem tarefa continua no quadro, com "Nada nesta etapa" no lugar da pilha: coluna é lugar, e não conteúdo.
- **Etapa vazia nasce recolhida** (2026-09-10, a pedido): numa lista de oito etapas, as que não têm nada só empurravam as que têm para fora da vista. Recolhida, a coluna vira um trilho na largura do alvo de toque, com a mesma etiqueta em pé (o nome em `writing-mode: vertical-rl`) — a mesma marcação virada de lado por CSS, então não existe um segundo cabeçalho para sair de sincronia. **A etiqueta é o botão que abre e fecha**, então tocar o cabeçalho é o caminho curto e o menu ficou sendo o longo; recolhida, o chevron duplo e o "+" não são desenhados, porque são coisas que se faz numa etapa à vista e num trilho de 44px empilhavam ruído. O cookie `sp-tarefas-etapas` guarda **só o que foi decidido no clique** (`etapa:1` recolhida, `etapa:0` aberta; `board-cookie.ts` grava, `parseStageOverrides` lê com zod), e não o estado das colunas: com o padrão sendo "vazia nasce fechada", uma lista de recolhidas não saberia dizer se a coluna foi fechada pela pessoa ou por estar vazia, e abrir uma vazia não sobreviveria à recarga.
- **O menu do chevron duplo** tem a ordem de dentro da coluna, que vale na hora e não fecha o menu (`keepOpen`, porque a pessoa experimenta mais de uma): por prazo, o padrão, com a mais próxima primeiro; por prioridade, a bandeira mais alta primeiro com o prazo desempatando; e por título, no alfabeto de pt-BR. A ordem é escolha **de coluna**, e não do quadro, e vive na sessão. Abaixo, recolher e expandir a etapa, e depois renomear e excluir, que só fecham o menu enquanto as etapas são uma lista em código.
- **O trilho** rola na horizontal e cada pilha rola na vertical, com o recuo da prancha devolvido em margem negativa para a rolagem começar na borda da tela. Cinco colunas de 19rem não cabem numa tela de 1440 ao lado do menu, e isso é o esperado num quadro: quem cede é o trilho, não a coluna. No celular a coluna vai a `min(80vw, 19rem)` e o trilho encaixa nela (`scroll-snap`), então o dedo passa de etapa em etapa em vez de parar no meio de duas. É a única tela com `Topbar` que **mantém a altura fixa também no celular**: as outras três crescem em fluxo e perderam a altura em 2026-09-09 para o topo não descolar, e o quadro não cresce, porque rola por dentro nos dois eixos.
- **O filtro vive na URL** e quem trabalha é o servidor (`list.ts` com zod, `list-options.ts` no lado leve, como nas outras listas): busca (título, descrição, identificador, projeto, etiquetas e os nomes de quem está envolvido, comparados por `slugify` dos dois lados), prioridade, prazo em três janelas (7 dias, 30 dias, qualquer) e "só atrasadas". O que já venceu conta como dentro de qualquer janela de prazo, porque é o mais urgente que existe. O quadro não tem paginação, então não há `pagina` nem `porPagina`. Sem nada que bata, a frase toma o lugar do trilho: cinco colunas vazias lado a lado leriam como quadro quebrado, e não como busca sem resultado.
- **A janela da tarefa** (`TaskDialog`, 2026-09-10, a pedido, adaptando uma referência de ficha de tarefa do usuário) é a **`Dialog` `xl`**, a mesma moldura de trabalho do editor de orçamento: o conteúdo à esquerda e a **atividade numa coluna própria de 22rem à direita**, cada uma rolando por conta, com o fio entre as duas e o topo sangrando as duas. Abaixo de 64rem a coluna da atividade desce para baixo do conteúdo, com o fio virando para cima; no celular a janela é a bandeja da casa e os textos descem um degrau pelos tokens redeclarados. Da referência vieram quatro coisas: a **rota no topo** (`Tarefas / <pasta do projeto>` com o identificador em etiqueta), que diz onde a tarefa mora e leva de volta ao quadro do projeto; os **campos em duas colunas** (`auto-fit` com piso de 13rem, então três em janela larga e uma no celular), com o rótulo e o glifo em cima e o valor embaixo, e não lado a lado como na ficha antiga, porque o valor de quase todo campo é objeto de largura própria e com o rótulo ao lado a ficha ficava em escada; o **"Vazio"** na tinta de `placeholder` no campo sem valor, que é o que diz que ele existe e pode ser preenchido em vez de parecer ficha quebrada; e a coluna de **atividade com o campo de comentário preso no pé**, que entra na lista na hora e vive na sessão, como as subtarefas marcam só na tela. O prazo mostra a data por extenso e só ganha a etiqueta colorida quando o tom de `dueOf` deixa de ser neutro, senão "13 set." e "domingo, 13 de set." ficavam lado a lado dizendo a mesma coisa; a etapa aparece em etiqueta no matiz dela, que é mais fino que a situação grossa, com o rótulo levando o glifo do quadro para o da etapa não sair repetido duas vezes. Fecha a coluna a fila de **o que dá para acrescentar** (vincular, subtarefa, anexo), declarada e ainda sem regra.
- **A ficha continua parecendo ficha, e é o valor que abre as opções** (acerto de 2026-09-10, a pedido, depois de uma rodada em que os campos viraram seletores e a ficha passou a ler como formulário): cada valor é desenhado como sempre foi — a etapa e a prioridade em `Badge`, o responsável em rosto com o nome, o prazo e o início por extenso, a estimativa em texto, as etiquetas em fila — e é o **clique nele** que abre o menu. Isso pediu duas coisas nos primitivos, as duas pequenas e reusáveis: o `DropdownMenu` ganhou **`triggerContent`**, que troca o botão de ícone por um botão sem caixa (`display: contents`, com o anel de foco indo no conteúdo) com o desenho de quem chama; e o `DatePicker` ganhou **`plain`**, que tira a moldura de campo e o glifo do calendário, mais **`display`**, o formato com que a data escolhida é escrita, porque sem moldura ela é valor de ficha e ali "domingo, 13 de set." diz mais que `13/09/2026`. Os menus já eram de vidro nos três primitivos, então o pedido de "todos no blur" não mudou nada. Os itens do menu ganharam **`media`**, o desenho que identifica a opção no lugar do glifo: é o rosto de quem pode assumir e a bolinha de cor de cada etiqueta.
- **Título e descrição se editam no lugar** (`InlineText`, mesma data, a pedido): o valor e o campo ocupam a mesma caixa com a mesma tipografia, então clicar não muda nada de posição, de tamanho nem de peso; sair do campo grava e `Esc` desfaz. O campo herda a escala do `Text` que o contém por `font: inherit`, em vez de repetir variante e peso, que sairiam de sincronia no primeiro acerto de tipografia; a altura é medida no próprio campo, porque `field-sizing` ainda não existe em todo navegador.
- **As etiquetas são escolha de uma gama pronta** (`features/tasks/tags.ts`, mesma data, a pedido), e não texto livre: trinta etiquetas em seis famílias (desenho, conteúdo, comercial, técnico, entrega, risco), cada uma com o próprio matiz, escolhidas no menu com a bolinha da cor ao lado do nome. O matiz é escolhido à mão, e não sorteado por hash: as famílias se reconhecem pela cor, e isso vale mais que ter trinta cores diferentes. Enquanto era texto livre, "Design", "design" e "Desing" conviviam.
- **Tudo o que a ficha muda vale só na tela** enquanto o domínio não está no banco, como as subtarefas já marcavam: quem ligar a tabela troca o `useState` do rascunho por uma Server Action com o mesmo `patch`. **As etapas que a janela oferece são as do quadro de onde a tarefa veio**, e não as do catálogo: mover para uma etapa que o projeto não tem deixaria o cartão sem coluna onde cair. O responsável e os envolvidos saem de `team`, que a página passa, somado a quem já está na tarefa, senão o responsável em vigor não apareceria marcado. A `key` da tarefa remonta o miolo quando outra abre, senão o rascunho de uma vazaria para a seguinte.
- **A subtarefa tem responsável, prioridade e prazo próprios** (`Subtask` ganhou `priority` e `dueDate`, mesma data, a pedido): os três saem do mesmo menu do chevron duplo na ponta da linha, em escolha única, porque três seletores por linha encheriam a lista, e quem escolhe pessoa vê o rosto e o nome. O prazo ali é uma lista de escolhas ("Hoje", "Amanhã", "Em 7 dias", "Em 30 dias", "Sem prazo") em vez de um calendário: numa linha de lista é o que se escolhe de verdade, e o calendário inteiro fica para o prazo da tarefa.
- **Cada parte da ficha é um container sem caixa** (`.block` em `task-sheet.module.css`, compartilhado com as subtarefas): o nome com a contagem no cabeçalho, a **ação de acrescentar na ponta direita e só em glifo**, e o corpo com o conteúdo ou com a frase do vazio. Vínculos, subtarefas e anexos existem mesmo sem nada, esperando o primeiro item. O fio, o fundo e o recuo saíram a pedido (mesma data): com eles a ficha era uma pilha de caixas com caixa dentro, porque o cartão do anexo e a linha do vínculo já têm as suas; o que separa uma parte da outra é o vão da coluna e o peso do nome. A descrição fica fora, em texto corrido.
- **Acrescentar abre janela** (`task-add-dialogs.tsx`, mesma data, a pedido), e não um campo solto: subtarefa (título, responsável, prioridade e prazo), vínculo (o seletor de registros, em que escolher já vincula, então não há botão de confirmar) e anexo (nome, endereço e tipo, porque não há onde guardar arquivo). As três na janela pequena de vidro da casa, com os campos no `Field` e o par de botões dividindo a largura no pé, na receita da confirmação de excluir clientes.
- **A coluna da conversa** tem 26rem, e não 22 (mesma data, a pedido): em 22 o cartão do comentário apertava a fila de ações. O fio de cima saiu — quem separa as colunas é o fio lateral — e o fundo virou um **véu de 2,5% da tinta do texto sobre o fundo da página**, no lugar do cinza agrupado da casa, que destoava por ser feito para caixa sobre página, e aqui é uma coluna da mesma página. No cabeçalho, o filtro entre **Tudo e Conversa**, que lê o `kind` novo de `TaskEvent` em vez de adivinhar pelo texto do `action`. No pé, **o cartão é o campo** (sobre a referência do chat do Claude): o texto mora dentro dele sem moldura própria, e a fila de ações fica no pé do mesmo cartão — anexar (imagem, documento, áudio), marcar alguém, marcar um registro, gravar áudio e enviar. Campo da casa aqui dentro daria duas molduras, uma dentro da outra, então o texto é cru e quem desenha é o cartão, como a barra de busca da página já faz com o `input` dela. Marcar escreve no texto e devolve o foco ao campo; os anexos esperam o armazenamento de arquivo.
- **A conversa é conversa** (mesma data, a pedido de "meio como se fosse uma conversa no WhatsApp", sobre referências de conversa de suporte do usuário): a coluna deixou de ser lista de atividade e virou fio de mensagens, do mais antigo para o mais novo, encostado no pé junto do compositor, com o **separador do dia** em etiqueta no meio ("Hoje", "Ontem", e depois a data por extenso) e a rolagem nascendo embaixo, que é onde está a última mensagem. Comentário vira **balão**: o rosto numa coluna fixa, o nome e a hora **fora** dele, em cima, e só o conteúdo por dentro. O **rabo** sai da quina de cima do primeiro balão de um bloco, do lado de quem falou, apontando para o rosto e o nome, que é a lógica do WhatsApp em grupo; a forma é a orelha curva que WhatsApp e Telegram desenham, feita como eles fazem, com um caminho em SVG usado de **máscara** sobre uma caixa pintada na cor do balão, então a curva é curva de verdade e nasce da quina sem emenda em qualquer fundo, porque não há segunda cor para casar. A quina daquele lado perde o raio, e o lado da minha bolha reserva os 10px que a orelha ocupa, senão a borda da coluna a cortava. **As duas pontas são neutras** (acerto do mesmo dia, a pedido, depois de uma rodada com o matiz da marca cheio na minha): quem diz que a mensagem é minha é o lado em que ela está e o "Você" em cima, e não a cor, e a minha fica um degrau acima no mesmo cinza da casa. **Mensagens seguidas da mesma pessoa entram como um bloco só**, sem repetir rosto, nome e rabo, com o vão curto entre elas e aberto entre blocos: é o que faz uma conversa longa continuar legível. Mudança de estado ("criou a tarefa", "concluiu a subtarefa") **não é balão**, porque ninguém falou: é linha de sistema com o rosto pequeno, a frase apagada e a hora na ponta. A lista guardada segue sendo do mais recente para trás, que é como a atividade chega do servidor; quem inverte e agrupa é a janela.
- **A conversa leva arquivo e áudio** (mesma data, a pedido): o "+" abre o seletor do sistema, em dois campos escondidos, um de imagem e um de documento (com um só, trocar o `accept` no clique chegaria depois de o seletor abrir), e o que foi escolhido fica na fila do comentário, com o × que o tira, no **mesmo cartão de anexo da ficha** — ele já abre o arquivo na tela, baixa, copia o link e mostra a prévia da imagem, então não há segundo desenho para manter. O microfone **grava**: o `MediaRecorder` começa no clique, o botão vira o ponto pulsando com o tempo correndo e o encerrar, e o que sai é um `blob:` que toca e baixa de verdade nesta sessão; permissão negada vira aviso, e não silêncio. O áudio publicado tem player próprio (`chat-audio.tsx`): tocar, a **onda** com o que já passou em cor cheia, o tempo que falta e o clique que pula para um ponto. A onda é desenhada a partir do endereço do arquivo, e não medida dele: medir exigiria decodificar o áudio inteiro no navegador, e o que ela precisa dizer é "aqui tem fala e ela está neste ponto". As contas de arquivo (tamanho, tipo pelo que o navegador diz, o anexo a partir do `File`) saíram da janela de upload para `features/tasks/files.ts`, porque agora são dois lugares fazendo a mesma coisa. Junto, a **CSP ganhou `media-src 'self' blob: data:` e `blob:` no `frame-src`**: sem isso o `default-src` recusava o áudio gravado e o PDF anexado por upload, e os dois ficavam mudos sem dizer por quê.
- **O Enter manda a mensagem** (mesma data, a pedido), e a quebra de linha fica no Shift; com a lista do arroba aberta, ele marca quem está na frente dela. O envio saiu do `onSubmit` para uma função só, porque agora três coisas chamam o mesmo caminho: o botão, o Enter e o que vem com arquivo ou áudio sem texto (áudio e arquivo falam por si, então mensagem só com eles é mensagem válida).
- **Uma marcação vira o registro que ela aponta** (mesma data, a pedido de "não economize nos detalhes"): acima do texto da bolha entra um **cartão** por registro marcado, com a mídia dele, o nome, o identificador em etiqueta e a linha de apoio; ele leva ao registro no clique e, ao apontar, abre a **ficha resumida** (`RecordHoverCard`, em `features/records/components/`, sobre a `HoverCard` da casa, a mesma peça do catálogo e da base de clientes). **Pessoa não ganha cartão** (acerto do mesmo dia, a pedido): ela já aparece por dentro da frase, com rosto e primeiro nome, numa pílula alinhada ao texto, e o cartão só repetia o que o texto diz. No meio da frase, o registro entra pelo **identificador**, e não pelo nome, que já está no cartão e ali quebrava a linha. O compositor mostra os mesmos cartões, com o × que tira a marcação e o sinal do texto junto.
- **O arroba escrito abre a lista de quem marcar** (mesma data, a pedido de "já listar as opções"): o trecho depois do último "@" sem espaço é a busca, comparada sem acento pelo `slugify`, e a lista aparece com rosto e nome no **desenho e na camada do painel do menu de opções** da casa, **flutuando** sobre o cartão do comentário (vidro, fio, sombra e o canto `xl`, em `position: absolute` ancorada no pé do compositor, a pedido): no fluxo ela empurrava o campo a cada tecla. Enter marca o primeiro dela, e escolher troca o que foi digitado pelo sinal inteiro. O botão "@" da barra segue existindo, para quem prefere procurar na lista inteira.
- **A estimativa é roleta, e não menu** (`DurationPicker`, em `components/ui/duration-picker/`, mesma data, a pedido, sobre uma referência de seletor em roletas): três colunas, dias, horas e minutos, cada uma com a seta de subir, a fila que rola encaixando de linha em linha (`scroll-snap`, 36px por linha) e a seta de descer, com a faixa da escolha na linha do meio de cada pista. O valor do meio é o escolhido, e a conta espera a rolagem parar, senão cada quadro da inércia viraria uma escolha. As faixas são **60 dias, 24 horas e 60 minutos de um em um** (a pedido), e por causa disso o dia da estimativa passou a ser o de calendário: `WORK_DAY` virou `DAY_MINUTES` em `labels.ts`, porque com dia útil de oito horas escolher 23 h viraria "2 d 7 h" no rótulo e a roleta mostraria outra coisa. O total sai em minutos, que é como a tarefa guarda. Na moldura e na receita do `DatePicker`: campo ou valor cru pelo `plain`, caixa flutuante no computador e bandeja no celular, com o vidro da bandeja, mais cheio, porque a roleta tem muita área vazia e a 20% o texto da ficha atravessava por ela.
- **O vínculo é um cartão com o × dentro** (mesma data, a pedido): quem tem fundo, canto e o desvincular é o container, e não o link, que estica por dentro dele e leva ao registro. O × fica **sempre à vista**, porque no toque não há apontar, e o cartão **não acende ao passar o ponteiro**: ele é a ficha do que está vinculado, e não uma linha de lista. O cartão tem 8px em volta, 8px entre a mídia e o texto e o canto `lg`, com o identificador ganhando ar do nome (acerto do mesmo dia, a pedido: estava tudo encostado). O fundo é sólido (`--color-bg-secondary`) porque a fila de artes agrupada precisa de uma cor de anel para separar as bolinhas, e ela sai daí por `--media-surface`. A mídia de cada tipo mora num lugar só (`RecordMediaView`, em `features/records/components/`): rosto para quem tem rosto, **fila de artes agrupada** para orçamento, na receita da coluna de orçamentos da casa (bolinha redonda com o véu do matiz do item, a arte com folga dentro, sobreposição apertada, anel na cor da superfície e o total ao lado), e o glifo do domínio no azulejo com o canto da casa para o resto, que é o que dá identidade a projeto, contrato e tarefa. Em `lg`, na cabeça de um resumo, ela cresce para 2,75rem e vira **uma arte só num azulejo** (`single`), como no catálogo e na base de clientes: a fila sobreposta com o total ao lado é desenho de linha de lista, e ali ela lia bagunçada (duas rodadas, as duas a pedido). O número de itens fica onde ele é fato.
- **O anexo mostra o que é** (mesma data, a pedido): na lista, imagem entra em miniatura de 44px no lugar do glifo, com `object-fit: cover` no azulejo, e o resto segue com a marca do serviço ou o glifo do formato; no upload, a prévia do arquivo escolhido nasce de um `blob:` criado por `useMemo` e solto no desmonte, senão cada redesenho penduraria um endereço na memória.
- **O estado vazio dos containers voltou a aparecer** (correção da mesma data): o corpo era `children ?? vazio`, e um `{condição && …}` que não passa chega como `false`, que o `??` não trata, então Vínculos e Anexos ficavam sem a frase. Agora quem decide é a contagem.
- **Os vínculos** (`links` no modelo, `links.ts` para o desenho) são o que a referência não tinha e o modelo pedia (pedido do mesmo dia): cliente, orçamento, projeto e contrato, cada um com azulejo no matiz e no glifo que aquele domínio tem no menu, o identificador, o nome e a linha de apoio (a empresa do cliente, o valor do orçamento), levando ao registro do outro lado. É o que tira a tarefa do vácuo e liga ao resto do sistema. Na prévia eles saem das prévias de verdade dos outros domínios, e não de um id escrito à mão, senão o vínculo seria link quebrado; o de projeto ainda cai em `/projetos/[id]`, que é rota vazia, como já acontece com os links de projeto do perfil do cliente.
- **A janela é uma só para o quadro inteiro**, guardando quem está aberto, e não uma por cartão: com vinte e quatro cartões seriam vinte e quatro janelas montadas, que é a mesma decisão da gaveta da base de clientes. Quem mostra poucos cartões abre pelo `TaskOpener`, que dá à linha papel de botão na receita do `DetailsTrigger` e carrega a própria janela: é o caso do bloco do painel, que tem cinco. O `DetailsTrigger` não serve mais para isto porque embrulha o conteúdo na `DetailsDialog`, uma janela pequena de vidro com rolagem própria, e as duas colunas não teriam onde rolar lá dentro.
- **O cartão** (`TaskCard`, 2026-09-10, sobre duas referências do usuário, pegando de cada uma o que ela faz melhor) tem o fio de duas camadas do `Card` e dos cartões de cliente e de orçamento, canto `xl` e `lg` no celular, com 8px entre as faixas, porque a 12px o cartão virava uma torre. Da primeira referência vem o corpo: a **prioridade** em etiqueta colorida abrindo o cartão (bandeira nos quatro tons de `priorityTones`), o **título** em `subheadline` semibold e duas linhas, a **descrição** em `footnote` secundária e duas linhas, as **etiquetas**, e um pé com os rostos de um lado e as medidas do outro. Da segunda vem a **linha de contexto** logo abaixo do título, colada nele por margem negativa porque é continuação dele: a pasta do projeto com o glifo, um ponto, e o **identificador** em algarismo tabular, o projeto cedendo por reticências e o identificador nunca encolhendo, porque é ele que a pessoa procura. O que o modelo tem e a referência não mostrava entrou onde rende mais: o **aviso**, em etiqueta só de glifo ao lado da prioridade (o texto mora na ficha; aqui ele diz que existe), e a **linha de trabalho**, com a `Progress` de um segmento por subtarefa no mesmo tom da ficha, a conta "2/4" e a **estimativa** na outra ponta, que juntas respondem "quanto falta" sem abrir nada. No pé, os rostos em `AvatarGroup` de até três com "+N", **o primeiro sendo sempre quem responde** (com responsável e envolvidos por extenso na leitura por voz, porque na tela são só bolinhas), e do outro lado as contagens de anexos e de atividade em glifo mais número, e o **prazo** na etiqueta de `dueOf`, que fica vermelha em "Hoje" e no vencido. Etiquetas, trabalho e as contagens só aparecem quando existem, então tarefa simples tem cartão curto e tarefa cheia tem cartão cheio. A ordem das faixas é a de quem varre a coluna com o olho: o que é urgente, o que é, onde mora, o que diz, como está classificado, quanto falta, e por fim quem cuida e quando vence. É `li` com papel de botão, e não um `button`, porque tem o leque por dentro e precisa decidir de quem foi o clique, como os cartões de cliente e de orçamento; o leque é o `TaskMenu`, no padrão dos outros (abrir e copiar o identificador funcionam, editar, duplicar, concluir e excluir fecham o menu). A estimativa e a conta das subtarefas viraram `estimateLabel` e `subtasksDone` em `labels.ts`, porque a ficha já escrevia a primeira e as duas passaram a ser lidas nos dois lugares.
- **Arrastar o cartão de etapa** (2026-09-10, a pedido, com o `@dnd-kit` que já estava instalado e mapeado para isto): o cartão inteiro é a alça, com a mão aberta ao apontar e fechada no gesto, e a folga de **6px** do sensor é o que separa arrastar de clicar, porque a mesma caixa também é o botão que abre a ficha. No ar, o cartão vira o mesmo desenho **inclinado 1,5° e erguido pela sombra** (`DragOverlay`, preso à janela pelo `restrictToWindowEdges`), e no lugar de onde ele saiu fica o contorno tracejado dele, para a pilha não pular de altura. A **etapa sob o cartão acende** num véu de 6% do matiz dela com o fio em 24%, e abre no topo da pilha o lugar do que vem, tracejado, dizendo "Soltar em <etapa>" — no topo, e não no fim, porque é a parte da coluna que está à vista quando o cartão chega. Quem recebe é a **coluna inteira, cabeçalho incluído** (`closestCorners` acha a mais perto pela quina, que é o que funciona com alvos altos e estreitos lado a lado): mirar a pilha de uma etapa vazia seria pedir precisão que ninguém tem com o cartão na mão. Soltar numa **etapa recolhida** move e **abre** ela, senão a tarefa chegava e desaparecia atrás do trilho fechado.
- **O gesto existe no teclado**, e as duas teclas do cartão se dividem: **Enter abre** a ficha e **Espaço pega** o cartão; as setas andam **de etapa em etapa** (um `coordinateGetter` próprio sobre os retângulos que o arraste já mediu, porque o padrão do sensor anda 25px e, com colunas de 19rem, mover uma tarefa pediria doze toques), Espaço solta e Esc cancela. Cada passo é anunciado em português pelo `announcements`. As duas teclas caíam na mesma mão até esta rodada, e a do cartão ganhava por vir depois do espalhamento dos ouvintes do gesto, então o teclado nunca movia nada.
- **Para onde cada cartão foi é um mapa por id** (`moved`), e não uma cópia da lista: o quadro em si continua vindo do servidor a cada filtro, e uma cópia sairia de sincronia na primeira busca; destino que o quadro em vigor não tem é ignorado, e a tarefa fica onde o servidor a pôs. A ordem **dentro** da coluna segue sendo a que o cabeçalho escolheu: arrastar muda a etapa, e não o lugar na fila. **Vale só na tela**, como o resto do que a ficha muda: quem ligar a tabela troca o `setMoved` por uma Server Action com o mesmo par (tarefa, etapa).
- A base de exemplo é `list-preview.ts`: 24 tarefas espalhadas pelas etapas, para toda coluna nascer com conteúdo e a contagem dizer algo de verdade, com datas relativas a hoje; a etapa de cada uma é sempre uma das que o projeto dela declara, porque etapa fora do fluxo do projeto não teria coluna onde cair. As cinco primeiras são as que já existiam para o bloco do painel, e o `preview.ts` do bloco passou a **sair daqui** em vez de ter lista própria: ele filtra o que fechou e ordena por vencimento, que é o que o bloco promete mostrar. A arquitetura de exemplo é `tree-preview.ts`, com duas pastas na raiz, uma pasta dentro de uma delas e o balde no fim. **O domínio não existe no banco**: quando as tabelas nascerem, muda só a linha da página e a do `AppShell`, porque quem filtra, distribui e conta é `buildTasksBoard` e `buildTaskTree`, que recebem as listas de fora.
- `/previa/tarefas` mostra o quadro sobre a `AppFrame`, sem sessão e só em homologação, como a prévia do painel, e `?projeto=<slug>` abre lá o quadro de um projeto, que em `/tarefas/<slug>` só se vê com sessão. O topo da aplicação não aparece na prévia, e isso é dela: o `Topbar` tira o nome de `navLocation`, que só conhece as rotas do menu.

No cartão, a contagem de atividade é do registro inteiro, e não de comentários: o modelo não separa um do outro, então o glifo é o de histórico, e não o de conversa da referência. ### Registros da aplicação

`features/records/` (2026-09-10, a pedido de "marcar literalmente tudo dentro da aplicação") é o índice do que existe e pode ser apontado: tarefa, cliente, orçamento, projeto, contrato, item do catálogo e pessoa da equipe. Vive em domínio próprio, e não dentro de tarefas, porque não é coisa de tarefa: é o índice da casa.

- **O modelo** (`records.ts`) é raso de propósito: chave única (tipo mais id, porque dois domínios repetem id), tipo, identificador que a pessoa lê, nome, linha de apoio e endereço. `recordKinds` diz como cada tipo aparece, com o glifo e o matiz que aquele domínio tem no menu. `RecordMedia` diz como ele se mostra: o rosto de quem é, ou as artes do que ele contém, com o matiz de cada item e o total, que é o que a fila agrupada precisa. E para o resumo que abre ao apontar uma marcação (2026-09-10), cada domínio preenche **etiquetas, fatos e uma nota**: os fatos levam a chave do glifo (`recordFactGlyphs`), e não o componente, porque o índice é montado no servidor e desenhado no cliente, como os glifos de projeto da árvore de tarefas.
- **O seletor** (`RecordPicker`) é uma peça só para duas perguntas iguais: a busca em cima, as abas por tipo (que **quebram linha** em vez de rolar, porque com sete tipos a rolagem escondia a última ponta sem avisar), e a lista agrupada, com o nome do grupo numa ponta e a contagem em etiqueta na outra, o realce de cada opção no canto da casa, e a mídia desenhada pela peça de registro (`RecordMediaView`): rosto para quem tem rosto, fila de artes para orçamento, azulejo do domínio para o resto. A aba "Todos" mostra os primeiros de cada tipo, e não uma lista corrida: com sessenta clientes e quarenta orçamentos, a ordem corrida enterrava as tarefas. Ele serve o **vincular registro** da ficha da tarefa, em que escolher amarra, e o **`#` do comentário**, em que escolher escreve o identificador no texto.
- **O índice de exemplo** (`preview.ts`) é montado a partir das prévias de cada domínio e **no servidor**, entregue por prop: são vinte e quatro tarefas, sessenta clientes, quarenta e dois orçamentos e trinta e seis itens de catálogo, e importar isso de dentro de um componente de cliente levaria as quatro prévias inteiras para o navegador só para mostrar nome e identificador. Os projetos saem dos que os clientes carregam na ficha, que é onde eles têm id de verdade. Contrato não tem registro nenhum porque o domínio ainda não tem prévia; o tipo existe esperando por ele.
- Pendências: a consulta de verdade, por `service.ts` com `api/v1`, no lugar do índice de prévia; e a paleta de comandos, que hoje só busca as rotas do menu, passar a ler daqui.

### Catálogo (produtos e serviços)

Rota `/catalogo`, no menu como "Produtos e serviços", página solta no grupo Área de trabalho com o glifo de etiqueta (2026-09-08; nasceu dentro da pasta Orçamento e saiu dela no mesmo dia, a pedido, junto com Clientes, que também deixou de ser pasta: "Clientes" e "Funil de vendas" viraram páginas soltas e a pasta sumiu, porque as duas bases se abrem o dia inteiro e um degrau a mais só atrasava): o catálogo existe para alimentar o orçamento, então é ali que se procura por ele. Feature `catalog`. Nasceu sobre uma referência de grade de cartões, adaptada à casa e à estrutura da base de clientes: `CatalogScreen` (Server Component) compõe o `Topbar` e a prancha `CatalogBoard` (cliente), que tem a `PageToolbar`, a grade e a paginação.

- **O item** (`summary.ts`) tem nome, descrição, tipo (produto ou serviço), categoria livre, preço em centavos, unidade de cobrança (por projeto, hora, mês ou unidade), prazo típico em dias só para serviço, foto opcional (`imageUrl`), matiz, ativo, datas de entrada e de atualização e, para a ficha ser completa (a pedido, 2026-09-08, porque é ela que faz o orçamento sair certo): custo direto e a margem que sai dele, desconto máximo sem aprovação, rodadas de revisão inclusas, dias de garantia ou suporte, o que a entrega inclui e o que se pede ao cliente (o escopo que o orçamento copia), etiquetas livres, anotações da equipe, os números de venda (orçamentos, aprovados, faturado, último orçamento) e os orçamentos recentes em que entrou. Sem foto, a arte é gerada (`artwork.ts`, DiceBear no estilo Loops, servida por `/api/artwork/[hue]/[token]` sobre `lib/generated-svg.ts`); o matiz vai como texto e tinge a arte, o azulejo dela e a etiqueta de preço. Referência `CAT-2026-0007` pelo `formatReference`, com o prefixo novo em `lib/utils/reference.ts`.
- **A grade rola por dentro no desktop e o pé fica preso** (pedido de 2026-09-08, porque a paginação subia e descia com a altura da grade): a prancha tem a altura da tela nas duas visões, a área dos cartões rola e o pé, alinhado à direita como o da tabela, mostra "Mostrando 1 a 12 de 36" e a barra quando há mais de uma página. Trocar de página rola a área da grade ao topo. O vão entre cartões caiu para 12px nas duas larguras (era 16 e 20). No celular tudo segue em fluxo.
- **O cartão** (`CatalogCard`) segue a referência: a arte do item num azulejo tingido no matiz dele (`CatalogArtwork`: a foto quando há, e sem foto a arte gerada, com a linha no matiz do item) e, na outra ponta, a situação (Ativo ou Inativo, antes do valor, a pedido de 2026-09-08), o preço numa `Badge` do mesmo matiz e do mesmo tamanho da de situação (também a pedido; o piso da grade subiu para 17rem para as duas caberem ao lado do leque) e o leque; nome em headline, descrição em até duas linhas na receita dos blocos do painel; acima do nome a linha de orçamentos, as bolinhas de até três clientes que já receberam orçamento com o item e o total ("12 orçamentos", "Nenhum orçamento"), e no pé **três etiquetas, e só três** (pedido de 2026-09-08, depois de uma rodada com "+N" e uma linha de fatos com "Desde", que saíram no mesmo dia a pedido), em ordem de peso: categoria, tipo na cor dele e estoque com a cor do estado ou prazo ("Prazo indeterminado" quando não há). ### Login

- Telas de autenticação são sempre escuras, por decisão de produto. O proxy manda o caminho no header `x-pathname` e o layout raiz põe `data-theme="dark"` no `html` quando `isAuthPath()` (`lib/auth-paths.ts`, a mesma lista que o proxy usa) bate, no servidor, sem flash e sem mexer no cookie de tema. Tentativa descartada: `color-scheme: dark` só no shell não funciona, porque o Chrome resolve o `light-dark()` das variáveis no `:root`, onde elas são declaradas, e não no elemento que as usa. Foi isso também que tirou o quadrado claro que aparecia no fim da tela no mobile: era o fundo do tema claro aparecendo abaixo do conteúdo.

Holofote largo (`spotlightRadius` 2.2) para o gradiente aparecer inteiro sem ponteiro, e órbita automática lenta quando não há movimento por 2,5s (no celular nunca há mouse). Ícones pelo `BrandIcon` (`components/ui/brand-icon/`): máscara CSS sobre o SVG de `public/brands/<nome>.svg` pintada com `currentColor`, a mesma técnica do `Logo`, então a marca segue a cor do botão nos dois temas. Com `color`, o SVG entra como imagem (`next/image`, sem otimização por ser SVG) na cor original: é o caso do Google, que tem quatro cores. GitHub e Apple são pretos no arquivo, e preto no tema escuro some, então ficam em `currentColor`, que é a versão oficial das duas marcas para fundo escuro. Nunca ícone de marca de outra fonte.
- O divisor "Faça login com e-mail" usa `--color-separator` no texto, a mesma cor das linhas, e sobe 12px para ficar colado à grade de provedores.
- Turnstile com o widget em modo **Invisible** no painel da Cloudflare (decisão de 2026-08-29): nunca desenha nada, então o container fica fora do fluxo (`position: absolute`, 0 por 0), sem cobrar nem o `gap` do grid. O `appearance: "interaction-only"` e o `size: "flexible"` ficam no código como rede de segurança caso o painel volte para Managed. Em desenvolvimento a chave de teste é a invisível (`1x00000000000000000000BB`), que espelha o modo do painel. O botão "Entrar" nasce desabilitado e só libera quando o widget devolve o token (`onVerify`), voltando a travar se expirar. Em desenvolvimento o `.env` usa as chaves de teste da Cloudflare (`1x000...AA`), que sempre passam; as reais ficam comentadas no mesmo arquivo para produção.
- Sem scroll no desktop: `.shell` tem `height: 100dvh` e `overflow: hidden`, e a coluna de conteúdo rola por dentro só se a altura não couber. No mobile o carrossel é `position: fixed`, então o fundo não acompanha a rolagem do cartão.
- Logotipo em 32px e título em `title1`, por pedido de presença. `devIndicators: false` no `next.config.ts` tira o indicador de desenvolvimento do Next, que atrapalhava a leitura da tela.
- Senha: `signInWithPassword` via `useActionState`. Rate limit `auth` por IP, Turnstile quando `TURNSTILE_SECRET_KEY` e `NEXT_PUBLIC_TURNSTILE_SITE_KEY` existem (`hasTurnstile()` em `lib/env.ts`; sem as chaves o widget não monta e a verificação não roda), zod em `signInSchema`, erro genérico "E-mail ou senha incorretos" para não vazar se o e-mail existe. Sucesso redireciona para `next` validado por `nextPathSchema`.
- "Relembrar senha" é comportamento, não enfeite: a action grava o cookie `sp-remember` (`1` ou `0`) e passa `remember` para `createClient`. Com `0`, `scopeToSession` em `lib/supabase/cookies.ts` tira `maxAge` e `expires` dos cookies do Supabase, no servidor e no proxy, então a sessão morre ao fechar o navegador. Com `1` (padrão), fica um ano.
- Erro nas telas de auth não é texto solto no formulário: vai para o `Toast`, pelo hook `useAuthToast` (`features/auth/components/use-auth-toast.ts`). Ele recebe título, mensagem e uma marca de identidade; a marca é o objeto de estado do `useActionState`, que muda a cada envio, então o mesmo erro repetido dispara o toast de novo em vez de passar despercebido. Cobre as três origens: erro da action, aviso de chegada (`?erro=` mapeado em `messages.ts` e o `#error` do fragmento) e Turnstile indisponível. Como o tom é `danger`, o toast fica na tela até a pessoa dispensar.
- `/auth/callback` entrou em `openPrefixes` no proxy. Antes, sem sessão, o callback era redirecionado para `/login` antes de trocar o código e o OAuth nunca fechava.
- Criar conta (`/cadastro`): mesmo `AuthCard` e mesmas duas etapas do mobile, com `SignUpForm` (`features/auth/components/signup-form.tsx`). O CSS é compartilhado em `auth-form.module.css` e os botões de provedor saíram para `OAuthButtons`, usados pelos dois formulários; nada duplicado. Campos: nome (vira `full_name` nos metadados, que a trigger de `profiles` lê), e-mail e senha com piso de 8 no zod (`signUpSchema`). A action `signUpWithPassword` repete o contrato do login (rate limit, Turnstile, erros amigáveis por `error.code`: conta existente, senha fraca) e chama `supabase.auth.signUp` com `emailRedirectTo` no callback. Com confirmação de e-mail ligada não há sessão na resposta: o formulário troca para o estado "Confirme seu e-mail" com o endereço enviado; se a confirmação estiver desligada, redireciona direto para `next`. Consentimento de Termos e Privacidade em texto com links abaixo do botão.
- Cadastro com e-mail já usado é bloqueado com "Já existe uma conta com esse e-mail" e link para o login. Com a proteção de enumeração do Supabase (confirmação ligada), o `signUp` de e-mail já confirmado devolve 200 com um usuário falso de `identities` vazio; é esse o sinal detectado (`data.user.identities.length === 0`, comportamento do `sanitizeUser` do gotrue). Para conta existente ainda NÃO confirmada o Supabase reenvia a confirmação e devolve o usuário real, então a tela cai no estado "Confirme seu e-mail", que é o desejado. Mostrar que a conta existe reabre a enumeração pelo formulário; decisão de produto consciente em troca de UX clara.
- Um usuário, várias formas de login: o Supabase vincula automaticamente identidades OAuth com o mesmo e-mail verificado ao mesmo usuário (padrão do gotrue, sem toggle para desligar). Google e depois GitHub com o mesmo e-mail viram UM usuário com duas identities; `profiles` não duplica porque a trigger é por id. Exceções que geram segunda conta: e-mail não verificado no provedor e e-mails diferentes entre provedores (GitHub com e-mail primário privado noreply). Conta nascida por OAuth ganha senha pelo fluxo de recuperar senha, unificando também o login por e-mail.
- Rate limit de auth em três camadas (`lib/security/rate-limit.ts` + `withinAuthLimit`/`withinEmailLimit` nas actions): por operação e IP (`auth`, 10/min), total por IP somando todas as operações de auth (`authTotal`, 30/min) e por e-mail alvo (`authEmail`, 5 por 15 min) nas ações que disparam e-mail (cadastro, reenvio, recuperação), onde limitar pelo alvo é o objetivo. No LOGIN por senha a chave é IP + e-mail e só FALHA consome a janela: `peekRateLimit` (leitura, sem consumir) barra antes de tentar e `checkRateLimit` registra só depois de senha errada. A revisão adversarial derrubou a primeira versão (chave só por e-mail, consumindo sucesso): 5 logins corretos em 15 min travavam o 6º, e qualquer pessoa com o e-mail da vítima travava o login dela com 5 POSTs por janela.
- Recuperar senha (`/recuperar-senha`): e-mail + Turnstile invisível, `resetPasswordForEmail` e estado de sucesso SEMPRE, inclusive quando o Supabase devolve erro (só loga no servidor). O `/recover` devolve 200 vazio para e-mail inexistente e o cooldown de reenvio (`over_email_send_rate_limit`) só existe para contas reais, então qualquer mensagem diferente viraria oráculo de existência; a revisão adversarial pegou exatamente isso na primeira versão. O e-mail usa o template recovery com token_hash, que leva a `/confirmar-email?type=recovery&next=/redefinir-senha`.
- Redefinir senha (`/redefinir-senha`): exige a sessão criada pela verificação do link; sem sessão mostra "O link não está mais ativo" com atalho para pedir outro. `updateUser({password})` exige aal2 quando o usuário tem TOTP (`insufficient_aal` no gotrue) e a sessão de recovery nasce aal1; o gate `mfaPending` do proxy resolve mandando para `/mfa` com `next=/redefinir-senha` preservado (única rota de auth cujo pathname sobrevive como next nos gates de MFA; `/confirmar-email` volta para `/dashboard` porque o `withNext` zera a query e o token_hash se perderia no caminho), o step-up eleva a aal2 e a troca acontece. Usuário logado pode acessar `/redefinir-senha` direto para trocar a senha; um `insufficient_aal` inesperado redireciona para `/mfa`.
- E-mails de autenticação com a nossa marca: 13 templates em `db/supabase/templates/`, os 6 de ação (confirmação, convite, magic link, redefinição, troca de e-mail e reautenticação) e os 7 avisos de segurança do painel (senha, e-mail e telefone alterados, forma de login conectada e removida, fator MFA adicionado e removido), todos gerados de um esqueleto único. Visual minimalista por decisão de 2026-08-30: fundo branco sem cartão, só o ícone da marca no topo à esquerda, título e texto soltos, botão preto pequeno só quando há ação, rodapé com linha fina, nenhum texto com ponto final. O ícone é `public/logotipo/specular-icon-email.png` (160px exibido a 40px): o ícone preto dentro de um chip branco com borda, tudo no próprio PNG, porque o modo escuro dos clientes de e-mail inverte fundo e texto sem tocar nas imagens e um ícone preto solto desaparecia no fundo escurecido. O chip sobrevive à inversão e fica legível nos dois temas. HTML de e-mail com estilos inline e tabela, logo em PNG (gerado do SVG, e-mail não renderiza SVG). `config.toml` aponta os 6 de ação para o ambiente local; no hospedado é colar tudo no painel e ligar o SMTP do Resend (tabela de slots e assuntos em `setup.md`). Cores literais aqui são exceção consciente: e-mail não tem tema nem tokens.
- Nenhum template de link usa `{{ .ConfirmationURL }}`: esse endereço vai direto ao `/verify` do Supabase e o token é de uso único, então scanner de e-mail corporativo consumia o link antes do clique e a pessoa via `otp_expired` na primeira tentativa. Os links apontam para `/confirmar-email?token_hash={{ .TokenHash }}&type=...` (página no grupo `(auth)`, mesma lista de `publicAuthPaths`, então tema escuro e acesso sem sessão), que mostra um cartão com título por tipo de link e só chama `verifyOtp` no clique do botão, via `confirmEmailWithToken` (server action com rate limit e zod em `token_hash` e `type`). Os estados de sucesso e de link incompleto (e o "Confirme seu e-mail" do cadastro) usam os ícones 3D de `public/3d-icons` (check e error) via `next/image` a 4rem de altura. Scanner faz GET e não consome nada. No sucesso a action redireciona para `next` e o proxy assume (primeiro login cai no `/mfa` pelo gate `mfaMissing`); o proxy não expulsa usuário logado do `/confirmar-email`, porque a troca de e-mail confirma com sessão ativa.
- A tela de confirmação do cadastro tem "Reenviar e-mail" (`resendConfirmation`, com rate limit e trava de 30s no botão), e o `/login` lê o fragmento `#error` que o Supabase devolve quando um link antigo falha e explica em português (link expirado ou usado), limpando o hash da URL.
- MFA (`/mfa`): uma rota, dois estados, tudo solto no AuthCard sem Surface (redesenho de 2026-08-30, seguindo o padrão das outras telas de auth). Com fator TOTP verificado, `MfaVerify`; sem fator, `MfaEnroll`: três ícones de autenticadores sobrepostos (Google Authenticator, Twilio e Microsoft Authenticator, este com o círculo preenchido no azul `#0078d7` do próprio logo, cor literal como exceção consciente de marca), título e descrição centrados, QR cru numa caixa branca sem padding e sem raio (decisão de 2026-08-31: limpo e funcional, a margem interna do próprio SVG basta), chave manual em UMA linha num box tracejado (`text-overflow: ellipsis`, fonte caption) com o "Copiar" dentro do box à direita (toast ao copiar) e `CodeInput` com `fullWidth`. O box é flex com padding de `--space-1` e a borda nele, não no `code`: assim o recuo do botão é o mesmo 4px em cima, embaixo e na direita, e a altura sai do próprio botão, que cresce para o alvo de toque no celular sem estourar a caixa. Não há botão de verificar: completar os 6 dígitos verifica sozinho nas duas telas, com "Verificando o código" durante a espera. A saída é "Sair da conta" em texto. Cantos pelo sistema da casa (`squircle()` no QR, na chave e nas caixas do código). No mobile a tela fica compacta: avatares e a linha de dica somem, o QR encolhe para 8.5rem e o gap cai para `--space-4`.
- O QR é um `<img>` com o data URL do Supabase direto no `src`: o `qr_code` vem como `data:image/svg+xml;utf-8,<svg ...>` sem encode, com aspas duplas dentro, que quebravam o `url("...")` de um `background-image` e o QR nunca renderizava (o bug só apareceu quando o enroll foi ligado no painel; o E2E anterior parava no skeleton). `next/image` não aceita data URL, então é `img` puro com o lint desativado na linha.
- `CodeInput` ganhou `fullWidth`: as caixas crescem por `flex: 1 1 auto` mantendo a base (3rem por 4rem no modo solto; raio lg via `squircle()`, dígito em `--text-title-2`). No `fullWidth` o gap cai para `--space-1` (4px) e as caixas viram QUADRADOS por `aspect-ratio: 1` com altura automática. Com `flex-basis: 0` e `width: auto` cada input voltava à largura intrínseca (~11rem) no cálculo de max-content, a trilha do grid estourava para ~70rem e o conteúdo inteiro saía da vista com scroll horizontal.
- O `.root` das telas de MFA usa `grid-template-columns: minmax(0, 1fr)`: sem isso a trilha implícita do grid cresce pelo max-content dos filhos (a chave em linha única, por exemplo) e a tela inteira ganha scroll lateral no mobile, que foi exatamente o bug reportado no iPhone.
- Confirmação de e-mail continua na aba original: `confirmEmailWithToken` para `type` signup/email não redireciona mais, devolve `done` e o cartão mostra "E-mail confirmado, volte para a outra aba" (com "Continuar por aqui" para quem abriu o link em outro aparelho). Ao confirmar, o cartão emite `confirmed` num `BroadcastChannel("sp-auth")`; a aba do cadastro (estado "Confirme seu e-mail") escuta o canal E faz polling da action `sessionEstablished` a cada 5s (os cookies são do navegador inteiro), e segue sozinha para `next` quando a sessão aparece. Os demais tipos (recovery, invite, magiclink, email_change) continuam seguindo na própria aba, porque o fluxo continua nela por natureza.
- As duas telas de MFA têm prévia na vitrine `/componentes` (grupo "Telas de autenticação"): `MfaEnroll` aceita `preview` com QR e chave falsos e pula o enroll no servidor, então dá para ver o layout em localhost sem sessão; a verificação da prévia falha de propósito. O fluxo real continua exigindo login em `/mfa`.
- `enrollTotp` passa `issuer: siteConfig.name`, então o autenticador salva a conta como "Specular" e não como o host do Site URL do projeto, que é o padrão do Supabase (a URI virava `otpauth://totp/app.specular.com.br:email`). O rótulo é gravado no momento do cadastro: quem já tinha cadastrado antes continua vendo o nome antigo no app até refazer o cadastro do fator.
- `enrollTotp` apaga os fatores TOTP não verificados antes de criar um novo, senão cada visita à tela acumularia um fator pendente; o componente ainda guarda um ref para não repetir a chamada no modo estrito do React.
- Cadastro convidado, não obrigatório (decisão de 2026-09-02): o `updateSession` devolve `mfaMissing` (aal1 sem próximo nível, ou seja, usuário sem nenhum fator verificado) e o proxy manda para `/mfa` na primeira rota protegida, mas a tela tem "Pular por agora". A `skipMfaEnrollment` grava o cookie `sp-mfa-skip` (httpOnly, 30 dias, contrato em `lib/mfa.ts`) e devolve a pessoa para o `next`; enquanto o cookie valer, o proxy para de convidar. Vencido, a tela volta a aparecer uma vez.
- **Step-up não se pula.** O cookie só silencia o convite de cadastrar: `mfaPending` (aal1 com aal2 disponível, ou seja, quem tem autenticador e ainda não digitou o código nesta sessão) continua barrando toda rota protegida sem olhar para ele, e a própria action recusa pular quando o nível seguinte é aal2. Quem pulou volta a cadastrar entrando em `/mfa` direto: sem nenhum fator a rota não devolve mais ao painel, justamente para ser esse caminho de volta.
- O conteúdo do `AuthCard` rola por dentro (`overflow-y: auto` no `.content`), porque o cartão do MFA é mais alto que a tela do celular e a página em si continua travada.
- `PasswordInput` (`components/ui/password-input/`): `Input` com `type` alternado e botão de olho na ponta, `aria-pressed` e rótulo que muda. O ícone de erro do `Field` entra antes do olho, porque o `Field` injeta `iconEnd` e o componente concatena em vez de substituir.
- O formulário não mostra asterisco: `required` vai direto no controle, e o `Field` só injeta `required` quando a prop dele é verdadeira (antes ele sobrescrevia com `false` o que o controle declarava).
- O `matcher` do proxy não usa a cláusula `missing` do exemplo da doc do Next. Ela isenta requisição de prefetch, e isenção do proxy significa rota protegida respondendo 200 sem sessão e sem CSP para quem manda `purpose: prefetch` na mão. O gate roda em toda requisição.
- Arquivo estático novo em `public/` precisa entrar no `matcher` do proxy (`logotipo`, `banners`, `bg`, `brands`, `3d-icons`). Sem isso o proxy trata a imagem como página protegida, responde redirect para `/login`, e o otimizador do `next/image`, que busca o arquivo por HTTP, recebe o redirect no lugar do PNG: a imagem quebra sem erro no console.
